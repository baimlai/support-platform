# 慢 SQL 调查 Skill

## 适用场景

- 工单描述“某条 SQL 或某个接口变慢”“订单列表超时”“慢查询突然增多”；
- 已知实例和时间范围，并且只做只读查询；
- 不适用需要变更、kill 会话、加索引、改配置等写操作。

## 需要收集的证据

1. **慢日志**：按平均耗时从高到低，拿到最慢 SQL 指纹、样例 SQL、执行次数、
   平均/最大耗时、平均扫描行数和返回行数。
2. **执行计划**：按指纹查询访问类型、命中索引、估算扫描行数和 Extra
   （例如 `Using filesort`、`Using temporary`）。
3. **实例监控**：CPU、IO 等指标，用来排除或确认资源瓶颈。
4. **锁等待**：采样窗口内是否存在等待样本。
5. **原始证据**：每条业务工具结果都会保存为 `ev-xxxxxx`。如果模型收到的内容
   被截断，使用 `evidence_read(evidence_id, offset, limit)` 分段读取原文，不要凭预览猜全文。

## 主要分支

- **慢日志为空**：可能是时间范围或实例不对，也可能是采样没有覆盖。
  标记为未验证，不要直接得出“没有慢 SQL”的结论。
- **执行计划全表扫描（`type=ALL`）或 `key` 为空**：候选原因指向访问路径或索引，
  但仍需要用真实 `EXPLAIN ANALYZE` 复核。
- **执行计划走索引但仍有 `Using filesort` / `Using temporary`**：
  候选原因指向排序或临时表开销。
- **监控失败或超时**：CPU/IO 相关结论标记为未验证，不能写成“监控正常”。
- **锁等待 `no_data`**：无样本不等于没有锁等待，必须保留这个限制。
- **工具报错**：错误本身也是证据的一部分。记录错误，继续其它分支，
  不要反复重试同一个坏接口。

## 结束条件

满足下面任意一条就应结束调查并输出报告：

- 慢日志、执行计划、实例监控、锁等待都尝试过（成功、失败或无数据都算尝试过）；
- 报告里的每条事实都有证据引用，无法验证的项明确标注“未验证”；
- 达到最大轮数或被取消。这时报告必须写明“调查未完成”，不能把中间说明当成最终结论。

## 输出要求

最终报告必须**先给结论**，再给建议和证据。Markdown 二级标题固定为：

```text
## 结论
## 修复建议
## 证据链
## 已排除与待验证
## 调查过程
## 验证方法
## 当前限制
```

### 结论怎么写

- 先写 `**现象：**`，一句话说明工单现象。
- 再写 `**最可能根因：**`，只给一个主根因，不要把多个假设平铺成清单。
- 再写 `**置信度：** 高 / 中 / 低`、`**直接证据：** [ev-xxxxxx]`、`**结论边界：**`。
- 证据充分时，不写“候选原因”章节；候选原因只出现在低置信度时，最多 3 个，
  按可能性排序，并写清还缺什么证据。
- **证据充分的标准**：有直接证据支持主根因，并且会改变修复方案的主要替代原因
  已经排除，或已明确说明不影响结论。
- **证据不足时**：结论第一句写“当前证据不足以给出唯一根因”，置信度标“低”，
  再列最多 3 个候选；不要把未验证项写成确定原因。

### 修复建议怎么写

- 按 `### 首选方案`、`### 备选方案`、`### 临时缓解` 分组，最多三组。
- 首选方案必须针对主根因；备选方案说明什么情况下改用它。
- 每条建议写清适用条件、预期效果、风险和验证方式。
- 不要把所有排查分支都变成建议；与结论无关的检查项放到“已排除与待验证”。

### 其它章节

- **证据链**：只列支撑结论的关键证据，带 `[ev-xxxxxx]` 引用。
- **已排除与待验证**：写清排除了什么、依据是什么；还缺什么证据、为什么会影响结论。
- **调查过程**：工具调用表格，供审计；前端会默认折叠。
- **验证方法**：只写验证主结论和首选修复所需的最小步骤。
- **当前限制**：工具失败、超时、无数据、模拟数据等限制。

通用规则：

- 观测事实和推断分开写，相关性不等于因果；
- 工具失败、超时、无数据都写“未验证”，不能解释成“没有异常”；
- 每条关键事实尽量带上 `[ev-xxxxxx]` 证据引用；
- 不要声称执行过任何生产变更，本轮只做只读调查和建议。
