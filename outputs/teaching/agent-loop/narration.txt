如果只把大模型当成一个更聪明的搜索框，你其实还没有用上 Agent。

模型不会自己连数据库，也不会自己看执行计划。它能做的，是根据眼前的上下文，决定下一步说什么、调什么工具。Agent 要做的，是把这句话变成一次真实的行动，再把行动的结果放回上下文，让它继续判断。这个一圈接一圈转下去的结构，就是 Agent Loop。

今天这一讲，我们不看概念图，直接对着这个项目里的循环代码，和一张真实的模拟工单，把这件事讲清楚。

先看最小版本。一次循环，只有四步：第一，准备上下文；第二，调用模型；第三，如果模型提出工具调用，就执行工具；第四，把工具结果写回上下文，再回到第二步。

模型回复是流式来的。循环一边收，一边把文字增量发给记录器和前端，不是等整段生成完才处理。每一次模型回复和工具执行，都包在一轮里。轮次开始、模型消息、工具开始、工具结束、工具结果、轮次结束，都有事件留痕。你在页面上看到的时间线，不是前端编的，是循环按真实顺序发出来的。

你可以把这一圈想成值班 DBA 问诊：模型是医生，工具是化验单。医生不能凭感觉下诊断，得先开检查；检查结果回来了，再决定要不要开下一项检查。

我们拿一张慢 SQL 工单走一遍。用户说：订单查询从今天十点开始明显变慢。

第一轮，平台把系统提示、工单和当前可用的工具一起交给模型。注意，这时候业务工具只有一个，查慢日志；另外还有平台自带的两个工具，search tools 用来搜索和加载工具，evidence read 用来分页读取证据。模型看不到执行计划，也看不到实例监控，因为平台还没有把那些工具声明放进来。

模型看完问题，提出第一次工具调用：查这个实例十点到十一点的慢日志。循环收到请求，先发一条工具开始事件，再校验参数，然后真正执行。

慢日志返回了一万六千六百五十八个字符。平台没有把这一大坨全部塞回上下文，而是把它保存成证据，只把四千字以内的预览、统计信息和证据编号交给模型。这个处理发生在工具执行之后、结果写回上下文之前，也就是 after tool call 这个钩子的位置。

下一轮，模型看到的是预览和证据编号。它判断信息不够，于是调用 evidence read，把证据往后翻了一页。再下一轮，它发现还缺执行计划，于是调用 search tools。平台加载了执行计划、实例监控和锁等待三个工具。注意，这三个工具不是在第一次请求时就给模型的，而是从下一次请求开始才出现。模型能看到的工具列表，每一轮都可以变。

接着，执行计划返回了，访问类型是 ALL，没有命中索引。实例监控超时了。锁等待返回无数据。

这里有两个特别容易讲错的地方：超时，是一个错误结果，不是没有异常；无数据，只能说明这次采样没有取到，不等于锁等待不存在。循环不会因为工具失败就崩掉，它把错误当成一条普通的工具结果交给模型，让模型自己判断下一步。这就是为什么这套系统能承认没查到，而不是硬编一个结论。

那循环什么时候停？这个项目里有几种结束方式。第一，模型不再提出工具调用，给出最终回答。第二，平台的 finish turn 钩子明确要求结束，或者工具结果本身要求终止。第三，达到最大轮数。第四，用户取消。还有一种不太好的情况：模型或适配器报错，循环也会结束，但会把原因标成 error，而不是假装完成。

这里要说清楚哪些是 Pi 的，哪些是我们加的。循环结构、事件顺序、工具调用和结果的消息形状，来自 Pi；最大轮数、工具超时和结束原因，是我们在 Pi 的低层循环之外补的。Pi 的低层循环本身没有轮数上限，它把这件事留给上层。我们把它放进来，是因为后台任务必须有刹车，不能靠模型自觉。

还有一个特别容易被忽略、但非常关键的细节：配对。模型提出的每一个工具调用，都有一个编号。工具结果必须带着同一个编号回来。哪怕这一轮提了三个工具，一个失败、一个超时、一个被取消，每一个调用也都要有对应的结果。否则下一轮的消息结构就是坏的，模型会开始胡编。循环里有一条底线：可以失败，但不能失配。

所以，Agent Loop 本身并不神秘。准备上下文，调用模型，执行工具，写回结果，再重复。真正决定它能不能干活的，是这四步之间的约束：工具能不能被看到，结果能不能有边界地放回去，失败会不会被误读，循环会不会停下来，以及全过程能不能被记录和复现。

模型负责聪明，循环负责可靠。
