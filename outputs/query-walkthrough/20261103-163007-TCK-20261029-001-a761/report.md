# 慢 SQL 工单调查报告（模拟 · 第 2 步）

## 结论
**最可能根因：** 慢 SQL `a1b2c3d4e5f6` 的访问路径缺少合适索引，执行计划为全表扫描（`type=ALL`、`key` 为空），并伴随排序开销；慢日志显示平均扫描 185000 行、只返回 20 行。

**置信度：** 中
**直接证据：** `ev-000001`、`ev-000002`
**结论边界：** 尚未执行真实 `EXPLAIN ANALYZE`，访问路径仍属于模拟计划推断；实例监控未验证；锁等待无样本，不能完全排除。

**现象：**
- 工单 `TCK-20261029-001`：订单列表查询变慢，部分请求超时
- 实例：`db-mysql-001`；业务库：`shop_order`
- 慢日志观测：最慢 SQL 指纹 a1b2c3d4e5f6：平均 2380 ms，最大 8120 ms，出现 1240 次，平均扫描 185000 行、返回 20 行（证据 `ev-000001`）
- 执行计划观测：执行计划访问类型 ALL，未命中索引，估算扫描 185000 行，Extra：Using where, Using filesort（证据 `ev-000002`）

## 修复建议
### 首选方案
1. 先在只读副本或测试环境对最慢 SQL 执行 `EXPLAIN ANALYZE`，确认实际扫描行数、回表次数和排序开销。
2. 确认全表扫描后，评估为过滤列和排序列增加联合索引；先评估写入放大、磁盘占用和变更窗口，再走变更流程。

### 备选方案
- 如果索引改动成本高，先尝试 SQL 改写：减少返回列、缩小过滤范围，或让排序走覆盖索引。

### 临时缓解
- 在业务侧限流、分页或缓存热点查询，避免高峰期放大；这只是缓解，不是根因修复。

> 以上建议仅用于只读排查；任何索引、参数或 SQL 变更都必须走变更流程。
