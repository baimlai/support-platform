## 3. 第 2 步实现范围（调查能力）

1. **慢 SQL Skill**：`skills/slow-sql/SKILL.md` 描述适用场景、证据清单、主要分支、
   结束条件和输出要求；`skill.json` 声明初始业务工具只有 `slow_log_query`。
2. **关键词工具搜索**：平台工具 `search_tools(query, limit)` 按工具名、标签、描述、
   参数名和中文别名打分；命中后加入**后续轮次**的可见工具。搜索不授予执行权限，
   未加载的工具调用会返回 `not found`。
3. **原始证据落盘**：`EvidenceStore` 把每条业务工具结果保存为
   `evidence/ev-xxxxxx.json`，并维护 `index.jsonl`。证据编号只能匹配
   `ev-\d{6}`，读取路径限制在当前运行目录内。
4. **有界结果与分页读取**：`EvidenceProcessor` 在结果超过 `max_inline_chars`
   时返回 `{truncated, evidence_id, size_chars, max_inline_chars, preview}`；
   平台工具 `evidence_read(evidence_id, offset, limit)` 按字符偏移读取原文。
5. **Topic**：`TopicManager` 从工具事件更新并持久化 `topic.json`，包含问题、
   范围、事实及证据引用、候选原因、未决事项、下一步、已尝试工具、证据读取记录、
   搜索记录。事实只来自工具实际返回的数据，推断放在候选原因里并标注状态。
6. **有界上下文**：`ContextBudget` 同时限制单条工具结果、Topic 和整份模型输入；
   超预算时按“系统提示词 + 工单 + Topic + 最近消息”裁剪，保证调用/结果配对。
7. **失败、无数据、截断的区别**：三者分别用 `is_error`、业务 `status=no_data`、
   `meta.truncated` 表示，报告中的措辞也不同，不能互相替代。

### 4.3 任务状态机

```text
queued ──► running ──┬──► completed   (stop_reason=completed)
                     ├──► failed      (stop_reason=error / max_turns)
                     └──► cancelled   (stop_reason=cancelled)
queued/running ──────────► interrupted (进程重启或关闭，stop_reason=interrupted)
```

- 状态值：`queued`、`running`、`completed`、`failed`、`cancelled`、`interrupted`
- `stop_reason`：`completed`、`max_turns`、`cancelled`、`error`、`interrupted`
- **`max_turns` 映射为 `failed`**：达到轮数上限时没有完成调查，不能算成功。
- 终态集合以 `TERMINAL_STATUSES` 为准，前端不要再自行维护一份。

### 4.4 存储

任务元信息在 SQLite（默认 `var/tasks.db`，WAL 模式）；运行记录仍在文件：

```text
var/runs/<task_id>/             # 运行目录名直接复用 task_id，方便按任务查文件
  run.json
  events.jsonl
  model_requests.jsonl
  model_responses.jsonl
  messages.json
  report.md
  topic.json
  evidence/
    index.jsonl
    ev-000001.json
```

`GET /api/tasks/{id}` 的 `run_id` 当前等于 `task_id`。

### 4.5 后台执行与取消

- `POST /api/tasks` 写入 `queued` 行后，用 `asyncio.create_task` 在当前进程后台执行，
  立即返回 `202`。
- 每个任务一个 `CancellationToken`。取消是**协作式**的：循环在检查点退出，
  已产生的事件和报告都会落盘，报告写“运行被取消，调查未完成。”
- `POST /cancel` 对运行中任务返回 `202`（快照可能仍是 `running`）；
  对已终态任务返回 `200`，幂等。
- **服务启动时**把上次进程遗留的 `queued/running` 任务标成 `interrupted`；
  **服务关闭时**先协作取消，超时后再硬取消，并标记 `interrupted`。
- 限制：任务不跨进程恢复，重启后只能看到“已中断”，不会自动续跑。

### 4.6 SSE

`GET /api/tasks/{id}/events/stream?after_seq=N`

- 先补 `seq > after_seq` 的历史事件，再每 0.5 秒轮询新事件；
- 帧格式：`retry: 1500`，每条事件为 `id: <seq>`、`event: <type>`、`data: <事件 JSON>`，空行分隔；
- 每 15 秒发一条 `: keep-alive` 注释保活；
- 任务进入终态且事件读完后，发送 `event: stream_end`，
  `data` 为 `{"status": "...", "stop_reason": "..."}`，随后关闭连接；
- 客户端断线重连时把最后收到的 `seq` 作为 `after_seq`，不会重复消费。
- 未知任务在开始流式响应前返回 `404`，避免先 200 再在流里报错。

### 4.7 可选模型（mock / deepseek）

默认仍然是 `mock`，保证零配置、离线可演示、自动化测试稳定。模型选择是**按任务**的，
不是全局开关：

```text
CLI:  --model-provider mock|deepseek --model deepseek-flash
HTTP: POST /api/tasks {"model_provider": "deepseek", "model_name": "deepseek-flash"}
```

服务端配置：

```bash
# Key 只放环境变量；适配器也接受 SUPPORT_PLATFORM_DEEPSEEK_API_KEY
export DEEPSEEK_API_KEY=sk-...
# 可选：换模型或接口地址
export DEEPSEEK_MODEL=deepseek-flash
export DEEPSEEK_BASE_URL=https://api.deepseek.com
```

- 适配器**不读取** `ANTHROPIC_API_KEY`，避免业务代码误用 Claude Code 的凭据。
- `GET /api/models` 返回 provider 的 `available` 和 `reason`；前端应把不可用项置灰。
- 显式选择 `deepseek` 但没有 Key 时，`POST /api/tasks` 返回 `422`，
  `detail` 提示设置 `DEEPSEEK_API_KEY`；**不会悄悄退回 mock**。
- 模型名优先级：请求 `model_name` > 服务端配置/`DEEPSEEK_MODEL` > 代码默认
  `deepseek-flash`。页面可选候选是 `deepseek-flash`、`deepseek-v4-pro`，
  也可用 `SUPPORT_PLATFORM_MODEL_OPTIONS` 追加。
- 任务创建时把 `model_provider` / `model_name` 写进 SQLite；任务快照原样返回，
  每轮模型请求的 `model` 字段也会记录实际模型名，便于核对“页面显示”和“实际调用”。
- 老数据库启动时自动补 `model_provider`、`model_name` 两列；历史任务默认算 `mock`。
- 实机验证：`deepseek-flash` 完成一张 5 轮调查，调用 `slow_log_query`、3 次
  `search_tools`、`evidence_read`、`execution_plan`、`instance_metrics`（模拟超时）、
  `lock_wait_query`，产生 4 条证据并输出带证据引用的报告。

### 4.8 真实 MCP 接入

业务工具不再由 Agent 进程直接 import 执行，而是由独立 MCP Server 提供：

```text
AgentRunner -> MCP Client -> JSON-RPC 2.0 -> FastMCP Server -> fixtures
```

- 运行时默认：官方 Python SDK `mcp`（`app/mcp/client.py`）；
- 传输：`stdio`（默认）、`streamable-http`（POST /mcp + SSE）、
  `sse`（旧版兼容/教学）；
- 协议：`initialize` → `notifications/initialized` → `tools/list` →
  `tools/call`，支持 `nextCursor` 分页；
- 结果：`content` 给模型，`structuredContent.details` 给平台，
  `isError=true` 表示业务失败而不是协议错误；
- 追踪：每次运行写 `var/runs/<run_id>/mcp_protocol.jsonl`；
- 能力目录：`GET /api/capabilities` 增加 `mcp` 段，显示传输、端点和服务名。

教学对照路线：

- `app/mcp/pi_style/` 手写 JSON-RPC 状态机，不依赖官方 `ClientSession`；
- 支持 stdio 和 Streamable HTTP，明确拒绝旧版 SSE（和 Pi 一致）；
- `uv run python -m app.cli mcp-compare --transport stdio` 并排调用两条路线；
- `tests/test_mcp_pi_style.py` 断言同一工具调用的文本和 `details` 完全一致；
- 协议细节、SSE 帧格式和调试方法见 `docs/mcp.md`。

当前边界：不实现 prompts/resources/sampling、OAuth、codemode、GET 长连接、
`Last-Event-ID` 续传、自动重连和常驻连接池。

### 5.2 任务

`POST /api/tasks` → `202`

```json
{ "sample_id": "slow-sql-001" }
```

或

```json
{ "ticket_text": "订单查询从今天 10 点开始明显变慢", "tenant_id": "tenant-demo" }
```

可选模型字段：

```json
{
  "sample_id": "slow-sql-001",
  "model_provider": "deepseek",
  "model_name": "deepseek-flash"
}
```

- `sample_id` 与 `ticket_text` **必须且只能提供一个**；都缺或都给 → `422`。
- 可选项：`skill`（不传时优先用样例工单里的 `skill`，再退回 `slow-sql`）、
  `max_turns`（1～30，默认 10）。
- 场景工单会按 `dataset` 字段加载对应模拟数据；路径必须在
  `fixtures/mock_dba/` 内且文件标记 `mock=true`，否则创建任务时直接 `422`，
  不会先返回 202 再在后台失败。
- `model_provider` 可选 `mock` / `deepseek`；不传用服务端默认值（默认 `mock`）。
- `model_name` 不传时用 provider 默认值；`mock` 固定为 `mock-dba`。
- 选 `deepseek` 但服务端没有 Key → `422`，`detail` 提示设置 `DEEPSEEK_API_KEY`。
- 未知字段（例如把 `ticket_text` 写成 `ticketText`）→ `422`。
- 自由文本会沿用第一个样例的 `instance_id`/`time_range`，生成新的 `ticket_id`
  （`TCK-<时间戳>-<随机>`），并标记 `source=user_text`、`mock=true`。
  前端应把 `ticket.description` 显示为用户原文，并保留“模拟”提示。

响应体是任务快照（创建瞬间）：

```json
{
  "task_id": "6700ec91-a402-4419-a7a1-6d6d9effe175",
  "status": "queued",
  "stop_reason": null,
  "ticket": {"mock": true, "ticket_id": "TCK-20261029-001", "...": "..."},
  "model_provider": "mock",
  "model_name": "mock-dba",
  "current_turn": 0,
  "turns": 0,
  "topic": null,
  "report": null,
  "error": null,
  "created_at": "2026-10-30T03:38:16.060462+00:00",
  "updated_at": "2026-10-30T03:38:16.060462+00:00",
  "finished_at": null,
  "run_id": "6700ec91-a402-4419-a7a1-6d6d9effe175",
  "evidence_count": 0,
  "capabilities": null
}
```

`GET /api/tasks/{task_id}` → `200`，字段同上。终态时：

- `report` 是 Markdown 全文；未终态为 `null`；
- `topic` 是最后一次持久化的 Topic（运行中也会更新）；
- `capabilities` 是 Skill/工具能力快照；
- `evidence_count` 来自证据索引行数。

`POST /api/tasks/{task_id}/cancel`

- 运行中/排队中 → `202` + 任务快照（`status` 可能仍是 `running`）；
- 已终态 → `200` + 任务快照；
- 未知任务 → `404`。

### 5.3 事件

`GET /api/tasks/{task_id}/events?after_seq=0&limit=200`

- `after_seq` 排他游标；`limit` 默认 200、最大 1000；
- 响应：`{events: [...], next_seq, has_more}`；
- `next_seq` 是本页最后一条事件的 `seq`；本页为空时等于请求的 `after_seq`；
- `has_more=false` 只表示“此刻没有更多事件”，**不代表任务结束**；
  是否继续轮询看任务状态。

事件顶层：`{seq, ts, type, turn, data}`，`turn` 对非轮次事件为 `null`。
事件类型：

```text
agent_start, turn_start, message_start, message_update, message_end,
tool_execution_start, tool_execution_end, topic_updated, turn_end, agent_end
```

`model_request` / `model_response` 只写运行目录，不进入事件接口。
`tool_execution_update` 接口保留，模拟工具不产生。

关键 `data` 形状：

- `tool_execution_start`：`{tool_call_id, tool_name, arguments, turn}`
- `tool_execution_end`：
  `{tool_call_id, tool_name, result: {content:[{type:"text", text}], details, is_error, terminate, duration_ms, meta}, is_error, duration_ms, turn, evidence_id}`
  - `data.evidence_id` 是这次调用**新产生**的证据编号，平台工具或没有落盘时为 `null`；
  - `result.meta`：`{evidence_id, truncated, raw_size_chars, max_inline_chars}` 或 `null`；
    成功的小结果也会有 `evidence_id`（每条业务工具结果都会落盘），但 `truncated=false`。
  - `result.details` 是业务工具自己的结构化结果。例如 `lock_wait_query` 的
    `details.status` 为 `no_data`、`details.sample_count` 为 `0`；前端应读这个字段，
    不要去解析 `content[0].text` 里的 JSON 字符串。
  - `is_error` 只表示工具调用失败（异常、超时、参数错误）；`no_data` 是正常结果，
    不是错误，两者不能混用。
- `turn_end`：表示**一轮模型响应结束**，不代表整个任务结束。
  `data.message.stop_reason` 为 `toolUse` 时，说明这一轮请求了工具、后面还要继续执行；
  整体是否结束看 `agent_end` 事件或任务状态。
- `topic_updated`：`{topic: {...}, turn}`；`turn` 为触发更新的工具所在轮次。
- `message_start/update/end.data.message`：消息对象；助手消息含
  `{role, content, stop_reason, error_message, timestamp, provider, model}`。
- `turn_end.data`：`{message, tool_results}`。
- `agent_end.data`：`{messages, reason, error}`。

`topic` 字段：

```text
question, scope, facts, candidates, open_questions, next_steps,
attempted_tools, evidence_reads, searches, updated_at
```

- `facts[]`：`{key, statement, evidence_id, source_tool, observed:true, data}`；
  `data` 是该事实对应的结构化观测值。
- `candidates[]`：`{key, statement, status, evidence[]}`；
  `status` 为 `candidate` / `supported` / `unverified`。
- `evidence_reads[]`：`{evidence_id, offset, limit, total_chars, truncated, is_error[, error]}`。
- `searches[]`：`{query, match_count, loaded[], is_error[, error]}`。

```text

```

### 5.5 状态码汇总

| 场景 | 状态码 |
|---|---|
| 创建任务（已受理） | `202` |
| 取消运行中任务 | `202` |
| 取消已终态任务（幂等） | `200` |
| 查询/事件/证据/报告成功 | `200` |
| 未知任务、样例、证据、轮次 | `404` |
| 报告未生成 | `404` |
| 请求体不合法（两个来源、缺来源、未知字段、未知 Skill） | `422` |
| 未知模型 provider，或选了 deepseek 但服务端没有 Key | `422` |

### 5.6 前端联调约定

- 过程更新先轮询，默认 1.5 秒；任务进入终态后停止。SSE 可选，事件形状与轮询一致。
- 后端任务状态是权威来源，页面刷新不取消任务。
- 前端不编造未返回的数据；缺失字段显示空状态。
- 工具卡片以 `tool_execution_start/end` 为准；随后的 `role=toolResult`
  `message_start/message_end` 是写回上下文的工具消息，不要重复渲染。
- 大证据只按 `offset/limit` 分段取，不一次性加载全部原文。
- 取消后继续轮询到 `cancelled`，不要点击后立刻把 UI 改成已取消。
- 所有页面都要显示 `mock=true` 提示：数据仅用于流程验证。
- 模型下拉框的数据来自 `GET /api/models`（或 `capabilities.models`）；
  `available=false` 的项置灰并展示 `reason`，不要默认选中。
- 创建任务后以任务快照里的 `model_provider`/`model_name` 为准展示“本次使用的模型”，
  不要用页面当前下拉框的值回填历史任务。

### 5.8 前端问题答复（2026-10-30，第 3 步更新）

1. **状态码**：见 5.5。`202` 只表示“已受理”，不代表完成。
2. **事件分页**：`after_seq` 排他；`next_seq` 是本页最后一条的 `seq`；
   `has_more=false` 不代表任务以后不产生事件。
3. **事件 data 形状**：见 5.3。`message_start/end` 也会为用户消息和工具结果消息发出；
   助手流式增量在 `message_update.data.assistant_event`。
4. **`evidence_id`**：在 `tool_execution_end.data.evidence_id`（顶层），不是 `result` 里面。
5. **`topic_updated`**：`data` 为 `{topic: {...}, turn}`；字段见 5.3。
6. **报告**：终态时已写完；终态之前 `404`；`structured` 固定 `null`。
7. **取消**：协作式；`202` 响应的 `status` 可能仍是 `running`，继续轮询到 `cancelled`。
8. **能力目录**：`skills[].content` 是 Skill 的 Markdown，可直接展示；
   `tools[].kind` 区分业务工具和平台工具。
9. **证据列表**：以索引文件字段为准，含 `is_error`；`preview` 只用于列表预览。
10. **重启**：服务重启后，之前未完成的任务变成 `interrupted`，不会续跑；
    前端应展示“已中断”，不要显示为运行中。
11. **CORS**：默认允许 `http://localhost:5173`、`http://127.0.0.1:5173`、
    `http://localhost:4173`、`http://127.0.0.1:4173`；换端口用
    `SUPPORT_PLATFORM_CORS_ORIGINS` 配置。
12. **`no_data` 的位置**：业务状态在 `tool_execution_end.data.result.details.status`，
    例如 `lock_wait_query` 的 `details.status="no_data"`、`details.sample_count=0`；
    `data.is_error` 仍为 `false`。前端不需要解析 `content[0].text`。
13. **`turn_end` 语义**：只表示一轮模型响应结束；`message.stop_reason=toolUse`
    说明后面还有工具执行。整体结束以 `agent_end` 或任务终态为准。

### 5.9 报告展示契约（2026-10-30，前端已落地）

报告仍是 Markdown，接口仍是 `{markdown, structured:null}`，没有新增结构化字段。
前端 `src/utils/reportMarkdown.ts` 按 `##` 标题切分，`ReportPanel.tsx` 负责展示。
后端写报告时使用下面这组标题；顺序固定，但前端不依赖序号，只认标题：

| 顺序 | 标题 | 内容 | 页面位置 |
|---|---|---|---|
| 1 | `## 结论` | 最可能根因、置信度、直接证据、结论边界；必要时附现象/候选 | 第一屏主卡片 |
| 2 | `## 修复建议` | 首选方案、备选方案、临时缓解 | 结论下方 |
| 3 | `## 证据链` | 事实和对应证据编号 | 折叠区 |
| 4 | `## 已排除与待验证` | 已排除项、待验证项和缺失证据 | 折叠区（警告色，默认排第一） |
| 5 | `## 调查过程` | 轮次/工具/结果表 | 折叠区 |
| 6 | `## 验证方法` | 上线前如何复现和确认修复 | 折叠区 |
| 7 | `## 当前限制` | 本次调查的边界和不确定项 | 折叠区 |

`## 结论` 内的标签格式：

```markdown
**最可能根因：** ……
**置信度：** 高 / 中 / 低
**直接证据：** `ev-000001`、`ev-000002`
**结论边界：** ……
**现象：**（可选）
**当前候选（按可能性排序，最多 3 个）：**（仅证据不足时出现）
```

约束：主结论只能有一个“最可能根因”和一个首选修复建议；修复建议可以有多个候选；
只有证据不足时才列出候选根因，且最多 3 个、按可能性排序、写清楚还缺什么证据。
不能把“待验证/候选”写成已确认结论。

前端兼容策略：

- 没有 `## 结论` 的旧报告不走主卡片，而是显示“报告未按标准给出单独结论”，
  再原样展示候选原因/现象；不会把候选原因提升成“最可能根因”。
- 不认识的 `##` 章节归入“其它章节”，不会丢内容；完整 Markdown 和原始 JSON
  仍放在折叠区，方便核对。
- 证据编号统一按 `ev-\d{6}` 提取，点击后打开证据详情抽屉；后端的编号格式不要改。

## 8. 当前边界

- 只读、本地模拟，不连接真实数据库/监控；
- 工具顺序执行，未实现并行；
- 工具搜索是关键词打分，不是向量检索；
- 上下文预算按字符估算，不是精确 token 计数；
- 任务在单进程内执行，不跨进程恢复；重启后未完成任务标为 `interrupted`；
- 无鉴权、无多租户隔离，CORS 只放行本地开发地址；
- 报告只有 Markdown，`structured` 固定 `null`；
- 任务列表/历史分页接口尚未提供，目前只能按 `task_id` 查询；
- DeepSeek 接入是 OpenAI 兼容协议适配，尚未做真实数据源；模型输出质量取决于所选模型；
- 没有 Key 时 DeepSeek 选项只展示不可用，不会自动降级成 mock。
