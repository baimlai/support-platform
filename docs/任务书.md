## 1 我们这次要做什么

用 Python 搭建一个能运行的 DBA 工单 Agent 小平台，将 Pi 内核中需要的部分移植为 Python，配一个独立 TypeScript 前端。用模拟的慢 SQL 工单、Tools 和 Skill，跑通从接收问题、调用工具、分析证据到输出诊断建议的完整流程。

用户希望通过亲手搭建和阅读代码，理解 Agent Loop、Tools、Skills、上下文、Topic 和执行记录如何配合，并清楚知道哪些来自 Pi、哪些是我们自己的设计。先简单、清楚、能跑起来，后续再逐项优化。

同事据说已有一版效果不好的 Python DBA 服务，目前没有代码可供检查。这次独立搭建不需要等待旧服务，也不代表已经决定推翻生产系统。`agent-platform` 只是此前查看过的参考项目，不是本项目的基础代码或必须使用的架构。

## 3 真实业务场景和难点

业务面向云数据库运维支持。客户或一线同事提交工单，例如“订单查询从今天 10 点开始明显变慢”。系统需要确认数据库实例、SQL 和时间范围，调用已有工具采集执行计划、慢日志、CPU、锁等待和变更记录，分析原因，提出有依据的处理建议和验证方法。

实际业务中，多个 DBA 小组已经提供大量封装好的工具，可能通过 MCP、HTTP 等方式调用。工具返回的 JSON、表格、文本格式各不相同。原则是尽量复用，不为了接入 Agent 就要求原小组全部重做接口；平台自己负责必要适配和结果处理。

主要难点如下。

| 难点 | 我们关心的行为 |
|---|---|
| Tools／Skills 可能有几百上千个 | 从问题找到合适能力，按需加载，不能把所有定义和说明都放进模型上下文 |
| 一张工单需要多轮取证 | 每轮能根据已取得证据决定下一步，避免重复查询、遗漏关键分支或过早下结论 |
| 工具结果多且格式不同 | 完整结果保存在模型上下文之外；大结果先筛选、统计或检索，再返回适量内容及引用 |
| 上下文越跑越大 | 同时控制单次结果和多轮累计大小；压缩或裁剪后仍能恢复调查进度 |
| 重要判断容易被摘要丢掉 | 用 Topic 保存事实、假设、证据引用、未决事项和下一步，而不是只留聊天摘要 |
| 结果不好但不知道错在哪里 | 看清每轮输入、工具选择、参数、返回内容、结果处理和最终依据 |

用户曾设想按问题大类拆多个 Agent，各自拥有 Tools／Skills，通过请求和结果交接，隔离上下文。这是后续探索方向；本轮先做单 Agent，不把多 Agent 当作解决效果问题的前提。

长期需要多租户、权限、审批和生产验证闭环；本轮只做本地只读模拟。数据按任务隔离，保留必要的租户标识，不建设完整生产权限系统。

## 4 技术方向和 Pi 移植要求

| 部分 | 本轮方向 |
|---|---|
| 后端与内核 | Python；服务接口建议 FastAPI |
| 前端 | TypeScript；建议 React＋Vite，先做单页工作台 |
| Pi 接入 | 选取必要内核源码移植为 Python，不通过 Node 服务调用原版 Pi |
| 状态与材料 | 本地 SQLite 保存必要任务和执行记录，文件保存原始工具结果；保持简单 |
| 工具与模型 | 模拟工具先行；模型走可替换适配器，之后接内部或外部模型 |

框架和基础库可以复用，不需要自己实现 HTTP 客户端、数据库驱动或全部模型协议。具体版本在开始编码时核对并固定。FastAPI、React、Vite 是此前讨论形成的默认建议；发现实际冲突时简要说明替代选择，不为选型重新铺开一轮框架调研。

### 4.1 Pi 先移植哪些部分

主要对照官方 Pi 的 Agent 核心，先阅读源码、选定并记录参考提交，再实现以下必要子集：

1. 模型请求、接收回复、执行工具、回传结果、继续或停止的 Loop。
2. 消息、工具调用 ID、工具结果之间的关联。
3. 每轮调用前准备上下文，以及工具执行前后的处理位置。
4. 运行事件、轮次限制、工具超时、取消等基本运行控制。

不整仓翻译 Pi，不同时搬运完整 Coding Agent、终端界面、插件市场和所有模型适配。若省略或改变原行为，写明原因及当前限制。

官方入口：[Pi 源码仓库](https://github.com/earendil-works/pi)  
官网文档：[Pi 官方文档](https://pi.dev/docs/latest)  
优先阅读：[Agent 循环源码](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent-loop.ts)  
配套说明：[Agent 核心说明](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)

源码与官网文档已于 2026-10-29 核对归属。`agent-loop.ts` 是循环核心入口，还需一起检查其引用的类型、流式接口和工具处理依赖，不能只翻译一个文件就宣称完成内核。`main` 与 `latest` 会变化；编码时固定参考提交，并核对所读文档与该提交的差异。

### 4.2 清楚标记来源并保留替换能力

把 Pi 对照内核集中放在后端 `app/runtime/pi_reference/`。模块说明中区分“Pi 源码移植”“参考 Pi 设计”和“我们自研”；Python 实现不能称为 Pi 官方原生 SDK。

用简短对照说明记录参考提交、原文件／函数、对应 Python 模块、改动和未实现项。可以写在 README 或一个小型 `docs/pi-mapping.md` 中，不要求额外编写大篇设计方案。实际复制、移植源码时保留相应许可和来源说明。

平台通过自己的运行接口使用内核。上下文组装和工具执行由接口注入，模型供应商细节放在适配器里；内核不直接依赖慢 SQL 规则、Topic 的数据库表或具体 DBA 工具。目录隔离之外，还要保证改上下文策略、工具结果处理或替换内核时，不必重写整个业务层。

参考 Claude Code 的公开设计即可，不要求复刻其全部产品，也不使用 Claude Agent SDK 或 OpenCode 作为本轮运行基础。

## 5 小平台怎么组成

以下是模块划分，不是微服务划分。文件数量保持适量，不为每个概念创建空壳工程。

```text
Python 后端仓库
  app/
    runtime/contracts.py       平台运行接口和公共类型
    runtime/pi_reference/      从 Pi 选择性移植的内核
    harness/                   上下文、工具、Skill、证据、Topic
    adapters/                  模型、模拟工具、存储等接入
    api/                       给前端使用的接口
  skills/                      慢 SQL 排查方法
  fixtures/                    明确标注为模拟的数据与案例

TypeScript 前端仓库
  src/                         工单输入、执行过程与结果展示
```

核心流程：

```text
输入慢 SQL 工单
  → 建立任务，加载慢 SQL Skill 和初始能力
  → 组装本轮上下文并调用模型
  → 模型提出工具调用
  → 工具网关校验并执行
  → 保存原始结果，返回有界内容和引用
  → 更新调查 Topic，再进入下一轮
  → 输出原因判断、证据、建议和验证方法
```

## 6 本轮需要实现的最小能力

### 6.1 一个慢 SQL 示例和少量工具

准备一张明确标注为模拟的慢 SQL 工单，以及约 3–5 个只读模拟工具，例如慢日志、执行计划、实例监控、锁等待、变更记录。至少让一个工具返回较多内容，演示保存、筛选和再次检索。至少能演示一次工具失败或无数据，不能把它解释成“没有异常”。

先用少量工具元数据实现简单关键词搜索，并按需向后续模型请求提供工具定义。无需首版接入上千个真实工具、向量数据库或复杂排序模型。搜索不自动授予权限，未注册／不可用工具的调用要明确报错。

提供一个慢 SQL Skill，说明适用场景、要收集的证据、主要排查分支、结束条件和输出要求。Skill 是调查方法，不要求再建立一套复杂插件框架。

### 6.2 工具结果、上下文和 Topic

不同源工具允许保留不同业务 Schema；平台提供统一的轻量结果说明，例如调用状态、可见内容、原始引用、是否截断和错误原因。短且相关的结果可以直接使用，不必每次额外调用模型摘要。

大结果先保存，再返回有大小限制的片段／统计和证据引用，提供按引用检索或分段读取的能力。未知格式或解析失败也必须受大小限制，不能回退到全量灌入上下文；检索文件须限制在当前任务材料内。

完整运行记录与实际发给模型的上下文分开保存。初版可使用“固定规则＋当前工单＋有界 Topic＋近期消息＋本轮必要证据”的简单策略，并设置可配置预算。字符限制或 token 估算要标清，不伪装成精确计数；裁剪不得破坏工具调用与结果的配对关系。

Topic 先做成简单、可持久化的结构：当前问题和范围、已知事实与证据引用、候选原因、未决事项、下一步。它不能无限追加全文，也不能把模型猜测直接写成已确认事实。复杂模型摘要和压缩优化可以后续再做，先验证裁剪旧消息后仍能恢复关键状态。

### 6.3 模型和运行记录

模型信息后续由用户提供。先实现模型适配接口和明确标注的模拟模式，让没有密钥时也能跑流程。模拟模型响应必须经过真实 Loop 和工具调用链路，不允许前端或接口直接返回一份写死报告。

模拟模式只验证软件流程，不代表实际模型已具备诊断能力。接入真实模型后，由模型选择工具和分析材料，不根据案例名称硬编码最终诊断。

记录任务状态、轮次、实际模型输入／输出、已加载能力、工具参数和状态、原始证据引用、处理后的结果及 Topic 变化。展示实际可取得的内容，不编造模型隐藏思考过程；模型凭据留在后端，不写入前端或日志。

至少支持基本超时、最大轮数和取消，避免无限循环。页面刷新不应取消后台任务；保存的记录可以重新查看。初版不要求进程重启后精确续跑，未完成任务应明确标为中断，不得假装已经恢复。

### 6.4 一个轻量前端页面

页面能输入工单或选择样例、开始任务、查看执行状态、取消任务，并查看以下内容：

- 每轮执行和工具调用时间线。
- 工具参数、处理后的结果和原始证据的有界预览。
- 当前 Topic、已加载 Skill／工具，以及每轮上下文。
- 最终诊断、证据引用、建议和验证方法。

使用后端真实任务接口；HTTP 提交和读取，过程更新可先用 SSE，也可为简化采用轮询并说明选择。不要只做静态页面或前端假数据演示，也不要把全部大日志一次加载到浏览器。

## 7 实施顺序和验收

- Rules： 翻译PI内核的时候，要标注每行或多行注释，大白话讲解，有必要则举例子。

按三步推进，每步都能展示运行结果，用大白话解释新增模块和 Pi 对照关系，用户确认后再扩展下一步：

1. **后端最小执行链。** 阅读并确定 Pi 参考源码，移植小型 Loop，接模拟模型和少量工具，通过命令行跑通多轮调用、正常结束和基本执行记录。
2. **补齐 DBA 调查能力。** 加入 Skill、简单工具搜索、原始结果保存与检索、Topic 和有界上下文，用慢 SQL 工单串起来，检查大结果和失败情况。
3. **接上前端。** 提供薄接口和单页工作台，真实调用后端，能查看过程、证据和报告；真实模型配置提供后再验证实际诊断效果。

交付时至少满足：

- 两个仓库分别给出依赖安装、启动命令、示例输入和配置示例；无模型密钥也能运行模拟流程。
- 一张慢 SQL 工单通过真实循环完成多轮工具调用，前端能看到过程和最终结果。
- 大结果完整保存在外部文件，模型只收到受限内容，需要时能按引用检索。
- 不同工具返回格式能接入，失败、无数据、截断有明确区别。
- Topic 持久化；裁剪旧消息后仍保留范围、事实依据、未决事项和下一步。
- 用户能从代码与对照说明识别 Pi 移植部分和 DBA 自建部分。
- 对正常调用、工具失败、大结果控量和停止／取消做必要验证，记录实际结果和当前限制。

先简单实现，不建设多 Agent 调度平台、容器沙箱、生产数据库变更执行、审批系统、复杂记忆系统或大规模插件市场。不要只交空目录、架构图或未接通的接口；最终必须能在本地运行。
