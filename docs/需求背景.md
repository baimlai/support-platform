## 0. 已确认约束

- **服务对象**：云厂商对外云客户，必须按多租户设计；内部一线/1.5线与外部客户共用一套 Agent 核心，多 Surface 接入。
- **使用模式**：内部 Copilot（一线快速定位、1.5线深度诊断/审批）+ 外部客户自助诊断（后续开放，只读、本租户范围）。
- **建设方式**：同事口头反馈已有一版效果不佳的 Python DBA 服务，代码尚不可得。用户进一步明确：当前希望先自己搭建一套，理解整套架构并学习 Pi；独立原型可以先行，不以取得旧服务代码为前置条件。生产是否重做、改造多少，仍需核实现状后决定。
- **Agent 内核**：用户希望通过独立搭建掌握机制，并进一步明确先把 Pi 必要内核翻译为 Python。采用选择性源码移植与必要适配，标清来源、改动及未实现部分；DBA 业务 Harness 独立设计。生产内核选择另行评估，不将学习原型等同于必须替换旧系统。
- **团队与建设节奏**：核心团队约 2–3 人，使用 AI 辅助编码；先讨论核心架构、各模块设计理念与协作，再逐项实现。尚未确认首版截止时间，不据此预设固定人数扩编或工期。
- **模型来源**：需要支持内部模型与外部多家模型，通过兼容协议和必要适配接入；具体供应商与主模型未定。模型接入不是当前讨论重点，大量业务能力如何帮助定位并解决问题才是重点。
- **存量工具接入原则**：用户澄清 Tools 已经封装好，返回 Schema／格式存在差异。优先复用现有调用与返回，不默认开展全面接口重封装或业务字段统一。平台当前重点是控制结果进入上下文的方式，必要时再做最小适配；非必要不要求原 DBA 小组改造。
- **结果与压缩要求**：无论返回格式如何，都要防止大结果及多次调用累计撑满上下文，并降低筛选、摘要和压缩造成的关键调查信息损失。用户希望 Topic 承载压缩时应保留的内容；其具体状态结构与保护机制需进一步验证。
- **讨论方式**：用户要求以老师和架构评审者的视角判断其想法，明确成立条件、漏洞和取舍；不能只迎合，也不能将用户尚在探索的实现方式直接登记为既定方案。
- **实施仓库与推进方式**：最新明确路径为后端 `/Users/baiml/PycharmProjects/support-platform`、前端 `/Users/baiml/PycharmProjects/support-platform-fe`，替代此前 NativeAI、WebstormProjects 路径及同仓双工程建议。两个仓库已只读确认，尚无应用源码；它们不是已确认的同事现有服务仓库。各放一份相同的 `任务书.md` 和 `需求背景.md`，其他模型重点按任务书实现；小步讲解、展示运行结果，用户确认后继续扩展。
- **源码理解与自主可控**：用户希望了解 SDK 的能力清单和内部机制，担忧仅使用 SDK 难以掌握系统，以及 Pi 停维护、撤包或不可用时平台中断。方案需要包含源码学习、依赖留存、可重建验证和业务边界，而非仅以开源或锁版本作口头保证。
- **自主优化与埋点**：用户明确希望后续自己优化压缩、上下文管理，在系统各节点设置埋点，可能仅需借鉴／复用 Pi 的 Loop。各环节应具有清楚的输入输出、可观测性及必要的同步控制边界，而不只提供最终结果日志。
- **语言选择条件**：用户已明确确认后端主语言采用 Python。此前个人习惯 Java、同事可能更熟悉 Go／Python 的背景保留；具体同事熟练度尚未盘点。已有服务通过 MCP 等边界复用，不要求改成 Python，也不视为全部已经统一协议。
- **当前学习目标**：用户最新提出自己先用 Python 或 TypeScript 搭建一套，以熟悉整体架构并了解 Pi。原型需能观察每轮输入输出、工具发现与执行、证据处理、Topic 更新和上下文变化，并标清 Pi 参考点、基础库复用与自建业务能力；语言提及两个候选不视为已正式改选 TypeScript。
- **前端工程**：用户要求 TypeScript 独立项目，并已指定前后端两个仓库。前端独立依赖、启动与构建，后端执行 Agent；先建设一页调查工作台，通过真实接口展示执行过程，不只展示静态聊天结果。
- **外部属性**：客户工单正文、日志、知识库均视为不可信输入；客户可见输出是产品的一部分，必须可审计、可审批。

### 0.1 用户提出的核心诉求

以下为用户明确表达的需求与原始设想。涉及具体实现的设想保留为待验证方向，不等同于已经批准的详细设计。

1. **以负责人视角推动落地。** 用户将主导方案实施，希望架构思想深刻、可落地，并能提升整体处理效果；不仅需要组件清单，还要解释为什么这样拆、各模块如何配合、哪些环节最影响质量。
2. **先讲清核心方案，再深入设计和编码。** 按“总—分—总”组织：先整体，再各模块，最后串回完整业务流程。用大白话解释，配合具体例子；内容详细但直白，避免黑话、空话和不必要的完整实现细节。
3. **主要难点是大量 Tools 与 Skills 的组织使用。** 要从工单正确定位问题，采集现场日志、CPU 等监控和埋点，分析证据并提出可执行、可验证的解决方案，而非只完成分类或生成回复。
4. **保留多 Agent 的领域隔离思路。** 用户设想按工单或问题大类配置 Agent，各自拥有 System Prompt、Tools、Skills，并能额外搜索工具；主 Agent 和下级 Agent 隔离上下文，通过请求与结果交互。分类维度、数量、搜索方式和交接格式需要进一步验证。
5. **不能把所有现场材料塞给模型。** 一张工单可能调用大量工具，工具结果需要考虑先落文件、使用 grep 检索、按 Topic 管理上下文，或用额外模型帮助检索和总结。这些是用户提出的候选方法，需要按材料类型和实际效果选择组合。
6. **路线确定后逐项攻克。** 优先把工具发现、Skill 装配、证据检索、上下文与记忆、调查判断、方案验证等问题拆清楚，逐步优化，而不是一次引入所有框架或铺开所有 Agent。
7. **方案要兼顾新知识与成熟经验。** 最近两周 AI 资讯用于学习、打开思路和补充候选能力；架构也要参考更早的成熟方案与行业常用方法，不能只按当次资讯选型。
8. **保留有价值的讨论。** 用户提供的业务背景、约束、思路、修正和已确定事项，应持续更新到本文件；新决策同步修正旧表述，保留未决问题，不把建议写成用户已确认的要求。
9. **平台兼容 DBA 小组已有工具。** 多个小组已经为过去的业务提供大量 Tools。用户倾向于保留它们现有的返回值，平台自行处理成适合模型使用的材料；“高质量输出”不应默认变成所有原维护小组的改造任务。
10. **优先解决结果与上下文治理。** 用户再次澄清：工具已封装，差异主要在返回 Schema／格式。关心的是内容过多时的二次筛选，以及压缩后仍能保留调查要点；Topic 是其希望承载这类要点的机制。方案应对此做独立审视，不把问题重心转成统一所有工具协议。
11. **接入过程中掌握机制。** 用户不仅要运行 Demo，还要知道 Pi 有哪些能力、调用链如何工作、哪些是自己的扩展。实现时用同版本源码、调用图和可运行的小实验讲解；不将复制代码、包装接口或阅读源码等同于全部引擎自主研发。
12. **评估独立内核并选择性吸收上游。** 用户建议可改用 Java、Python、Go 等语言，参考 Pi SDK／源码自行实现；以后由 AI 对比上游版本，将有价值的改进增加到自己的系统。该建议需要比较自主维护的收益与完整责任，不能自动理解为复制全部 Pi 功能或已确定新语言。

## 1. 结论先行

当前目标架构是：

> **确定性工作流 + 主 Agent 路由 + 领域子 Agent 执行 + 受控工具网关 + 独立验证 + 事件化数据回流**

原型先独立实现和验证小型循环；生产运行能力取得现状后再比较保留、局部替换和自研的必要性。能力目录负责按需发现 Tools／Skills；证据服务负责保存和检索大量工具结果；Topic 保存每个调查问题的进度与依据。明确领域的工单可直接交给领域 Agent，不要求所有任务都经过多层模型转述。当前为目标能力，不代表必须按图重建全部生产模块。

但需要明确六条底线：

1. **主 Agent 不是“万能大脑”**：分类、路由、权限、审批、重试、终止条件应由平台工作流控制，模型只做理解、判断和生成。
2. **上下文隔离必须用契约弥补**：子 Agent 只回传结构化结果和证据引用，主 Agent 不加载子 Agent 的全过程日志。
3. **工具输出是最大的上下文污染源**：在工具网关层收敛为“摘要 + 结构化证据 + 原始数据引用”，不能把原始日志直接灌给模型。
4. **多租户不是加一个 tenant_id**：数据、工具凭据、知识库、策略、配额、成本都要按租户隔离。
5. **埋点与数据回流不能后补**：事件模型、版本号、bad case 归因、标签质量分级必须从第一版开始设计。
6. **一套 Agent 核心，多种使用面**：内部一线、1.5线、外部客户共享分类、诊断、工具和事件模型；差异通过角色、工具白名单、知识视图、输出策略和审批流控制，不复制多套系统。

## 2. 背景与问题

- DBA 工单类型杂、专业性强，定位高度依赖个人经验，处理时长和质量不稳定。
- 诊断证据分散在监控、日志、配置、变更记录、历史工单中，单 Agent 上下文天然吃不消。
- 单 Agent 处理全量工单会出现：上下文膨胀、工具误选、长日志淹没关键信息、错误无法定位。
- 缺少统一埋点，无法回答“错在工具、模型、上下文、路由还是知识库”。
- 历史处理结果大多是非结构化文本，无法直接用于评测、few-shot 和模型训练。
- 对外云客户意味着多租户、SLA、数据合规和客户可见输出质量要求，不能沿用内部工具的宽松假设。
- 已有 Tool/Skill 数量多、来源杂，接口、权限、输出质量和可观测性不统一，直接挂载会把问题带进 Agent。
- 使用者不止一个角色：一线要快、1.5线要深、外部客户要自助；同一套能力必须按角色裁剪，而不是维护多套系统。
- 内部人员服务多租户，跨租户访问必须按工单指派/授权控制，不能默认全可见。
- 即使模型接口已经接通，仍可能因找错工具、漏加载方法、现场材料过量、摘要遗漏或子任务交接不全而诊断失败，不能把所有问题都归因于模型。
- 工单症状与根因可能跨类别：慢 SQL 可能关联锁、存储、流量或应用发布，初始分类不能把后续调查方向锁死。

## 3. 目标与非目标

### 3.1 目标

| 编号 | 目标 | 衡量方向 |
|---|---|---|
| G1 | 缩短工单处理时长 | MTTR P50/P90 下降 |
| G2 | 提升诊断准确率与一次解决率 | 根因命中率、重开率、人工改判率 |
| G3 | 降低人工介入与单工单成本 | 人工处理时长、token/工具成本 |
| G4 | 建立可归因、可评测、可训练的数据闭环 | bad case 归因覆盖率、数据集规模与质量 |
| G5 | 形成可复用的工具 / Skill / 子 Agent 扩展机制 | 新领域接入周期 |
| G6 | 满足多租户隔离、SLA 与合规要求 | 跨租户事件为 0，审计可追溯 |
| G7 | 支持一线、1.5线、外部客户多角色协同 | 升级率、自助解决率、人工介入率 |

### 3.2 非目标（第一期）

- 不做无人值守的高风险生产变更。
- 不做通用聊天助手，只处理 DBA 运维工单。
- 不替换现有工单系统、监控系统和 CMDB，只做智能编排层。
- 不一开始就训练模型；先做评测集、few-shot 和规则/检索基线。
- 不追求“所有工单全自动”，优先覆盖高频、低风险、证据充分的场景。
- 不在未获得客户授权时，将客户数据用于跨租户训练或共享。
- 第一期不开放外部客户自助变更；外部自助先做只读诊断与原因分析。
- 不复制完整编程终端、通用插件市场或无限递归的 Agent 团队；先验证真实工单收益。
- 不把兼容协议、模型返回成功或一张功能表，当作工具调用、长任务和业务效果已经验收。

## 4. 核心设计判断

1. **保留 Multi-Agent 扩展，按责任和实际收益拆分。**
   - 一级按**资源/产品领域**拆子 Agent：MySQL、PostgreSQL、Redis、网络、备份、权限等。工具、权限、上下文策略天然按领域聚拢。
   - 二级按**工单类型/场景**用 Skill/Playbook 表达：连接失败、CPU 高、慢查询、扩容失败等。
   - 只有当某类工单需要完全不同的工具集、上下文策略和评测标准时，才升级为独立子 Agent，避免 Agent 数量爆炸。
   - 一个领域 Agent 是可复用的角色配置，每张工单调查建立独立会话；领域配置、运行实例和调查 Topic 是不同概念。

2. **主 Agent 负责编排，不负责全量推理。**
   - 工单生命周期由状态机驱动，保证可审计、可恢复、可重放。
   - 分类和路由优先用“规则/错误码 + 小模型 + 大模型兜底”，低置信度转人工，而不是让主 Agent 自由发挥。

3. **上下文隔离的代价是信息丢失，必须用结果契约弥补。**
   - 子 Agent 输出：结论、根因候选、置信度、证据引用、未决问题、建议动作、成本。
   - 主 Agent 只消费契约；需要细节时按 evidence_ref 回查，不重新加载全过程。上下文隔离与受控证据共享同时存在，不能让子任务变成无法核对的黑盒。

4. **工具是上下文污染和错误的主要来源。**
   - 每个工具必须有统一 schema、风险等级、超时、幂等、并发安全、成本、版本和负责人。
   - 工具输出必须可截断、可摘要、可追溯到原始数据，避免“一次查询把上下文打满”。

5. **多 Agent 会增加路由错误和成本，必须可度量。**
   - 首版建议先完成一个领域、1–2 类场景；不预设必须有 3–5 个领域 Agent。标准并行采集优先由程序组合工具，不为每个采集动作增加一个 Agent。
   - 持续统计路由准确率、跨领域误派率、单工单 token 与工具调用成本。

6. **数据回流要区分“事实”和“模型输出”。**
   - 分开保存工具观测、人工修正、客户确认和模型推断，并记录来源、范围与质量；工具返回仍可能错误、不完整或过期，模型自评不能替代确认。
   - 训练和评测优先使用专家确认、客户确认、指标验证过的数据。

7. **自动化必须分级。**
   - Shadow（只建议）→ Copilot（人工确认后执行）→ 低风险自动化 → 分级自动化。
   - 高风险动作默认人工审批，任何阶段都不允许模型直接持有生产凭据。

8. **多租户是架构约束，不是字段约束。**
   - 每个租户需要独立的工具凭据、知识库视图、策略、配额、成本账本和审计视图。
   - 检索、缓存、记忆必须带租户边界，禁止跨租户召回。
   - 内部人员默认只能访问被指派工单对应的租户资源；跨租户访问需授权、限时和审计。

9. **客户可见输出是产品的一部分。**
   - 对外回复必须经过敏感信息、内部拓扑、其他租户信息检查。
   - 低置信度、高风险或涉及赔偿的回复必须人工确认。

10. **已有 Tool/Skill 是资产也是风险。**
    - 接入前由平台完成契约适配、权限评审、输出质量评估和版本登记，不默认要求原维护小组重写工具接口或返回格式。
    - 未认证的工具/Skill 不进入生产白名单。
    - 统一的是平台对 Agent 暴露的接口和结果，不要求上游存量系统先统一。原始接口、平台适配器、对模型可见的能力分别登记，方便追踪问题发生在哪一层。

11. **运行内核与业务资产分离，按实际自主需求选择复用层次。**
    - 完整 Pi SDK 为原方案；用户可能仅需 Loop，需比较底层循环复用与有限自研，避免复制完整编程助手。
    - 平台控制面（队列、执行归属、事件、权限、评测）独立于 AgentRunner；循环或会话完成不代表工单解决，会话恢复不保证外部动作可以安全重试。
    - 参考 Claude Code 的按需取材料、工具反馈、子任务隔离等公开机制；是否采用具体机制由 DBA 案例验证，不声称掌握或复刻其全部内部实现。

12. **角色差异用策略表达，不要复制 Agent。**
    - 同一领域子 Agent 服务一线、1.5线和外部客户时，通过 persona policy 控制可用工具、知识视图、输出模板和审批流。
    - 避免为每个角色维护一套 prompt、工具和 Skill；否则版本和评测会失控。

**多租户隔离的五个面**：

| 面 | 隔离内容 |
|---|---|
| 数据面 | 工单、事件、证据、日志、向量库、缓存 |
| 工具面 | 凭据、资源授权、工具白名单、配额 |
| 知识面 | 公共知识、租户私有知识、跨租户案例（需授权） |
| 策略面 | 模型路由、审批流、自动化边界、SLA |
| 运营面 | 成本账本、审计、指标、告警 |

### 5.4 端到端流程

```text
内部工作台 / 客户自助门户 / API / IM
      ↓
接入与归一化（租户识别、身份/角色、幂等、脱敏、附件）
      ↓
分类与打标（产品/资源/症状/根因/严重性/可自动化程度）
      ↓
主 Agent / 工作流路由（角色策略、租户策略、配额、工具白名单）
      ├─ MySQL 子 Agent ──┐
      ├─ PG 子 Agent    ──┼→ 结构化结果契约 → 汇总与决策
      └─ Redis 子 Agent ──┘
      ↓
诊断报告（证据链）→ 方案（风险/回滚/验证）→ 审批
      ↓
执行（受控工具、幂等）→ 独立验证 → 回复/关闭
      ↓
事件库 → bad case 分析 → 评测/数据集 → 提示词/工具/Skill/路由优化
```

> 同一张工单可同时存在“内部诊断视图”和“客户安全视图”；两者共享事实，但可见字段、可用工具和输出内容不同。

### 5.5 工单状态机

```text
RECEIVED → NORMALIZED → CLASSIFIED → ROUTED → DIAGNOSING
→ PLAN_READY → WAITING_APPROVAL → EXECUTING → VERIFYING
→ RESOLVED → CLOSED

异常：任意阶段 → NEED_HUMAN
      EXECUTING → UNKNOWN_SIDE_EFFECT
      任意阶段 → RETRYABLE_FAILURE / DEAD_LETTER
```

上图表示目标闭环，不要求首版开放执行。只读版本在方案完成后进入人工复核／待处理／待验证；已有外部处理结果时可进入验证。分别记录调查完成、动作完成、指标恢复和客户确认，不能把 Agent 结束直接映射为 RESOLVED。等待补充信息、暂停与人工接管应保存进度；事件回放用于查看过程，不自动重放生产动作。

## 6. 功能需求

优先级：P0 = 所属阶段必须；P1 = 首期增强；P2 = 后续演进。执行、审批等 P0 在开放相应能力时验收，不要求只读首版提前实现完整生产变更链路。多领域配置和子任务能力也不代表首版必须上线多个领域或多个常驻 Agent。

| SKL-09 | Skill 目录也分范围与按需发现，固定所用版本 | P0 | 不将上千条 Skill 简介全部放进系统提示；同名冲突和不适用版本在平台侧处理 |
| SKL-10 | Skill 声明证据能力依赖，平台解析到具体工具 | P0 | 上游工具替换或适配升级不要求批量改写 Skill；加载方法不自动授予执行权限 |

**存量 Tool/Skill 接入流程**：

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 盘点与分级：按领域、风险、使用频率、负责人分类 | 资产清单 |
| 2 | 平台侧契约适配：沿用原接口，以适配器统一模型侧输入输出、错误语义与超时；外部副作用另行核对 | 无须上游整体改造的接入包装与结果处理规则 |
| 3 | 权限评审：租户边界、凭据、资源授权、数据脱敏 | 安全评审结论 |
| 4 | 质量评估：成功率、延迟、输出大小、结果新鲜度、空结果率 | 质量基线 |

接入资料优先从现有接口说明、调用代码、脚本帮助和授权样本中提取，平台可用 AI 辅助起草目录与解析规则，再做样本核对。工具业务含义、单位、访问边界无法确定时，只向维护人集中确认这些必要问题，不能靠猜测上线。原维护小组负责源业务能力，平台团队负责适配、模型侧描述、结果整理和检索。

> 对外云客户场景下，数据使用权必须分层：平台运行数据可用于平台稳定性优化；租户业务数据默认只用于该租户服务；跨租户评测、训练和案例库必须获得合同授权并完成脱敏去标识。

**标签质量分级**：

```text
L0 模型自报结果
L1 工具返回但无人确认
L2 专家修正或审批
L3 客户确认 / 工单关闭
L4 后续指标与复现证明有效
```

> 训练和评测优先使用 L2–L4；不要把 Agent 自己生成的答案直接当训练标签。

质量标记应对应具体字段与依据，不能整张工单统一盖章。客户确认恢复或工单关闭，不自动证明根因、索引建议等所有结论正确；专家审批某项动作，也不等于确认全部诊断。评测时隔离事后结案答案，避免将正确答案提前放入调查材料。

## 7. 指标与验收

> 以下数值为早期建议目标，未经用户确认，不作为当前承诺或首版硬性门槛。先使用可取得的代表性历史工单与人工基线校准，不要求等待固定月份的数据才开始试点。所有指标按工单类型、优先级、领域分层统计，不能只看全局平均值。首版以诊断质量、人工补做量、有效覆盖和每张有效工单成本为主，自动关单不是先决目标。

### 7.1 业务指标

| 指标 | 定义 | 建议目标 |
|---|---|---|
| MTTR | 从受理到关闭的时长，统计 P50/P90 | 首期降低 ≥30%，成熟期 ≥50% |
| 首次响应时间 | 受理到首次有效回复 | ≤5 分钟 |
| 自动解决率 | 无需人工处理即关闭的工单占比 | 首期 ≥20%，成熟期 ≥50%（限低风险） |
| 人工介入率 | 需要人工接管/审批的工单占比 | 降低 ≥40% |
| 一次解决率 | 首次处理即关闭、无重开的占比 | 提升 ≥15 个百分点 |
| 重开率 | 关闭后重新打开的占比 | 不高于人工基线 |
| 单工单成本 | 模型 + 工具 + 人工复核 + 重开/回滚成本 | 降低 ≥30% |
| 客户满意度 | 工单评价 | 不低于人工基线 |
| 租户 SLA 达成率 | 按租户统计响应/解决 SLA | 按合同要求 |
| 一线自助解决率 / 升级率 | 一线无需升级即解决的占比 | 提升解决率，降低升级率 |
| 客户自助解决率 / 转人工率 | 客户自助会话中解决或转工单的占比 | 首期只读诊断，按试点校准 |

| 指标 | 说明 |
|---|---|

| 可审计 | 全量事件保留 ≥1 年（可配置），关键操作不可篡改 |
| 隔离性 | 租户、资源、工单、会话四级隔离 |
| 版本化 | 模型、提示词、工具、Skill、知识库、策略、Agent 配置全版本化 |
| 集成性 | 通过适配器对接现有工单、监控、日志、CMDB、变更系统，不替换 |
| 多租户 | 租户级配置、配额、数据、成本、审计隔离；支持运营开通 |
| 多 Surface | 内部工作台、客户门户、API/IM 共享同一 Agent 核心与事件模型 |
| 数据区域 | 按合同支持数据驻留；跨区域访问需授权 |
| 合规性 | 数据最小化、脱敏、可删除，满足对外云服务审计与隐私要求 |

## 13. 架构讨论形成的核心思路

本节保留与需求相关、值得继续验证的方案思路。完整 Pi SDK、有限自研均为此前讨论分支，内核边界见第 13.10 节、语言讨论见第 13.11 节；生产改造原则见第 13.13 节，用户最新明确的独立学习原型目标与架构建议以第 13.14 节为准。下文 Pi／TypeScript 特定机制保留为原路线及设计参考，不作为当前强制依赖；后续继续修订，不把每个候选技术都加入首版。

### 13.1 Pi 复用与业务自建边界

| 部分 | 当前建议 | 为什么这样分 |
|---|---|---|
| 运行内核 | 复用 Pi 的模型接入、工具循环、会话、压缩和运行事件 | 避免从裸模型接口重造整套运行能力 |
| 能力加载 | 复用 Pi 的 Skill 加载及 Tool Search／MCP 扩展，按固定版本装配验收 | 复用发现和加载机制；SDK 中需要显式配置相应扩展，不照搬 CLI 默认行为 |
| 工作方式 | 借鉴 Claude Code 的按需读取、工具反馈和子任务上下文隔离 | 让调查逐步获取材料，主调查者不承受所有中间过程 |
| 业务流程 | 自建工单状态、任务归属、预算、等待、人工接管与恢复 | 会话进度不能代替业务进度，队列重试不能保证外部动作只执行一次 |
| 领域方法与能力目录 | 自建 DBA Skill 内容、工具适用说明、认证、版本和发现评测 | 工具搜索能否找到正确能力、方法是否适合现场，依赖业务定义 |
| 证据与记忆 | 自建证据索引、持久材料、派生视图、Topic 和经验确认规则 | 文件和摘要需要能复查、受权限控制，并能在重启后继续使用 |
| 生产控制 | 自建工具网关、审批绑定、执行状态核对和独立验证 | 运行内核没有云数据库工单所需的业务授权与结果判断 |
| 评测与运营 | 自建真实案例、人工纠错、失败归因和版本比较 | 验证是否减少完整人工工作量，而非只看模型生成量 |

Claude Agent SDK 提供较完整的运行能力，但第三方模型的兼容接入不等于整套功能得到 Anthropic 官方支持。当前采用 Pi 的理由是多模型与可嵌入性更贴合需求，不表示 Pi 或某个模型天然更擅长 DBA。具体能力与模型效果需按固定版本进行业务验收。[Pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)、[Pi Skills](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md)、[Claude 子任务机制](https://code.claude.com/docs/en/sub-agents)、[Anthropic 网关边界](https://code.claude.com/docs/en/llm-gateway)

### 13.2 模块如何协作

| 模块 | 核心责任 | 与下一模块交接什么 |
|---|---|---|
| 工单接入与业务流程 | 识别可信身份、资源、影响、时段，管理状态 | 授权范围内的工单事实、任务和预算 |
| 协调与路由 | 选择领域与方法，处理跨领域及模糊问题 | 调查目标、领域配置、必要证据引用 |
| 领域调查 Agent | 根据方法查证，比较原因，决定下一项检查 | 工具请求、Topic 更新、子任务请求或诊断方案 |
| Tools／Skills 目录 | 在可用范围内发现、装配所需能力 | 少量候选、工具定义或排查方法正文 |
| 受控工具网关 | 校验权限与容量，调用数据源，保存结果 | 状态、统计、覆盖范围、原始材料及证据引用 |
| 证据存储与检索 | 保存原始观测，提供统计和有界片段 | 可核对来源、时间／行号、限制及相关材料 |
| Topic 与上下文管理 | 保存事实、假设、证据、缺口、下一步，控制模型当前材料 | 能继续调查的精简上下文与持久进度 |
| 专业子任务 | 在独立范围内分析大量材料或专项问题 | 发现、支持／反对证据、限制和建议，不回传全过程 |
| 复核、执行与验证 | 人工评审方案，按授权实施，以新证据检验效果 | 动作状态、指标对比、业务确认与交接事项 |
| 工作台与反馈评测 | 展示进度和依据，接管、纠错、比较版本 | 可归因的修正和回归案例 |

逻辑模块可以共处于一个应用和后台 Worker 中，不要求一模块一服务。领域 Agent 的上下文独立，证据通过同一受控服务共享；只共享有权限的事实和引用，不共享全部聊天历史。跨领域或专业任务的创建均经过平台登记，父子任务共同受工单预算和取消规则约束。

### 13.3 大量工具与材料的处理选择

工具装配分为常驻基础能力、场景常用工具、按需发现工具。搜索先缩小权限、领域和版本范围，再做关键词或语义匹配；新增加的工具必须能解释适用条件和结果限制。常用取证形成标准组合，避免模型重复寻找已知能力；特殊工具仍能按需发现。

材料处理按类型选择，不统一变成文本摘要：

| 材料 | 首选方式 | 必须保留的限制 |
|---|---|---|
| 日志文本 | 时间／请求标识过滤，grep／rg 检索片段 | 查询范围、命中位置、截断和采样情况 |
| 慢查询记录 | 按 SQL 指纹聚合次数、耗时、扫描行数 | 数据覆盖率；样本占比不代表全量或 CPU 占比 |
| CPU、I/O 等监控 | 时间序列和事前事后对比 | 采样粒度、缺失点、指标单位和业务负载 |
| 执行计划 | 结构化解析，查看访问路径、排序和估算 | 估算与实测不同；涉及实际执行的工具单独控制 |
| 文档与历史案例 | 关键词及必要的语义检索 | 来源版本、适用条件、确认状态和租户权限 |

原始观测保存一次，统计、摘要等作为可重建的派生视图；重复采集是否复用取决于时间、新鲜度和现场变化。工作文件不是永久业务状态，文件检索也不能绕开证据权限。额外模型适合解释复杂片段，但不应先把全部材料压成不可复查的摘要，再让主调查者只相信摘要。

Topic 按“待回答的问题”组织，例如扫描量、锁等待、存储延迟、近期变更。Topic 的开合与 Agent 数量解耦；当前调查者只加载必要材料，关键事实、失败检查、反对证据和未决事项持久保存。对外输出应区分观测、推断与已验证结论。

### 13.4 慢 SQL 工单的完整走查

讨论样板：客户反馈订单查询在某个时段开始变慢、部分请求超时，MySQL CPU 较高。此为示意场景，未取得客户真实工单；不把例子中的时间、数字、SQL 指纹或根因写成真实业务事实。

| 步骤 | 主要协作 | 必须产出的结果 |
|---|---|---|
| 1 受理与定范围 | 接入、身份授权、工作流 | 正确实例、版本、时区、时段、影响、诉求；缺失信息明确 |
| 2 装配方法与初查 | 路由、慢 SQL Skill、基础工具组合 | 监控、主要慢查询、可得的锁与等待、近期变更，结果入证据服务 |
| 3 建立调查问题 | MySQL Agent、Topic | 区分扫描量增加、调用量变化、锁等待、存储异常等候选；标明支持、反对和缺口 |
| 4 定向深入 | 工具发现、证据检索、按需专业子任务 | SQL 差异、执行计划、索引或其他相关材料，避免无目标地遍历所有工具 |
| 5 判断与复核 | 主调查者、证据、必要人工 | 可核对的主要原因候选，明确尚不能确认什么；相关性不直接当因果 |
| 6 形成方案 | 领域 Agent、DBA 复核 | 临时缓解和长期优化、业务语义、影响、实施条件、停止／恢复措施、验证方法 |
| 7 处理与验证 | 首版人工实施；后续审批和执行器；独立验证 | 用新证据在可比条件下检查目标 SQL、资源、错误率及其他负面影响 |
| 8 回复与回流 | 工作流、客户安全视图、人工反馈 | 区分调查完成、动作完成、指标恢复、客户确认；修正转成有依据的回归案例 |

查不到材料、工具超时、采样不完整都不能解释为“没有该问题”。只读首版可以准确缩小范围并交接，不需要声称每张工单都找到最终根因；若要关闭工单，必须满足该业务场景的验证与确认条件。

### 13.5 技术栈与实施顺序建议

| 层次 | 建议选择 | 选择原则 |
|---|---|---|
| 调查运行 | TypeScript、Node.js、Pi Coding Agent SDK | 与 Pi 直接集成，固定验收版本；已有业务系统不因此整体迁移 |
| 应用接口 | 当前默认推荐 TypeScript＋Fastify | 服务工单、任务、管理和工作台，与 Pi Worker 共用业务约定；用户确认后纳入实施基线 |
| 业务与索引 | PostgreSQL | 保存工单、Topic、任务、配置、证据索引和反馈 |
| 原始材料 | 公司对象存储或 S3 兼容存储 | 按权限、保留期和材料大小管理 |
| 后台任务 | 优先复用已有系统；没有时评估 pg-boss 等成熟组件 | 持久任务、取消、重试和执行归属；业务副作用另行核对 |
| 检索与统计 | 元数据过滤、全文检索、rg、结构化聚合 | 先建立可解释基线，再按证据引入向量检索或分析沙箱 |
| 人工工作台 | React 或团队熟悉的前端框架 | 展示依据和进度，便于复核、纠错和接管 |

先采用模块化应用加 Worker 的简单部署，不叠加多套 Agent 编排、工作流和记忆框架。两三个人可以借助 AI 编码分模块推进，但必须先约定工具与证据、Topic 进度、任务交接这三类共同契约，用同一张工单做端到端验收。新增工具主要改注册与适配，新增场景主要改方法和配置，不应每次重写整个平台。

首轮优先验证三条链路：能找到正确能力；能从大量材料中持续调查并接管恢复；能输出有依据的方案并验证结果。之后才按瓶颈扩展专业子任务、更多领域、辅助总结模型和受控执行。

### 13.7 Tools 与 Skills 的管理搜索和接入方案

**复用已封装工具，优先治理进入上下文的内容。** 当前主要问题是不同返回 Schema 下的大结果与累计上下文控制，不以全面重封装工具或统一业务字段为前提。已有调用能直接复用时保留，仅在必要边界做适配、目录补充、访问控制和结果处理。以下适配与解析方式是可选手段，按需要采用，不要求全部先建完。平台无法恢复源端未返回的数据，也不能把不明确的字段含义推断为事实。

**区分三种搜索。** 工具搜索回答“用哪个能力取得材料”；Skill 搜索回答“按什么方法调查”；证据搜索回答“已经取得的材料里，哪些内容回答当前问题”。它们可以共用部分基础设施，但需要不同目录和返回结构，不能把工具说明、操作方法与客户日志混成一个搜索库。

#### 13.7.1 目录与分工

| 资产 | 平台保存什么 | 维护原则 |
|---|---|---|
| 源工具记录 | 原接口／脚本、所属小组、使用说明、原参数、示例结果、访问方式、能力限制 | 尽量从现成材料建立，不强求上游改名或改格式 |
| 面向 Agent 的工具 | 稳定标识、可回答的问题、适用条件、输入结构、风险、结果含义、源工具映射 | 由平台适配，必要时将同义能力归并；含义不同保留差异 |
| 结果处理规则 | 格式识别、字段映射、单位与时间语义、聚合、质量检查和版本 | 先复用格式处理器，再补少量工具专属规则，避免每个工具单独写一套 |
| Skill | 简介、适用范围、调查步骤、证据要求、能力依赖、停止条件、输出要求和版本 | 排查方法独立于 DBA 小组内部接口名称；平台将依赖映射为已认证能力 |

可以用 AI 从现有资料生成候选说明与规则，但需核对授权样本后发布。平台不知道的关键语义列为待确认，不默认当作可用。重复能力按覆盖范围、时效、可靠性和成本选择默认来源，不把多个小组功能相似的工具都同时塞给模型。

#### 13.7.2 从几百上千个工具定位能力

1. 从工单确定授权资源、产品和版本、时段、调查目标；权限来自可信配置，不由模型自己声明。
2. 依据场景装配少量常用工具与必需 Skill，常规取证不必从全目录重新搜索。
3. 需要新证据时，先明确要回答的问题，例如“同一 SQL 指纹在事发前后的次数与扫描量是否变化”。
4. 在授权目录内按产品适用性、数据历史范围、读写风险等过滤；来源字段尚未确认的，不伪装为确定匹配。领域筛选保留公共监控和变更能力，跨领域线索可请求协调者处理。
5. 精确名称／别名、关键词和必要的语义匹配产生少量候选；按适用性与可靠性选工具，不只按文本相似度或使用热度排序。检索引擎先做可解释基线，再用漏召回案例决定是否增强。
6. 返回用途、适用条件、输入要求、局限和默认来源理由，加载所选工具的完整定义；找不到时可浏览分类或在既有授权内放宽非权限筛选，不无限重复同一句搜索。

工具调用不保证只找一个：同一问题可能需要两种互补证据。重要的是查到正确材料，而不是命中某个固定名称。

#### 13.7.3 加载到 Pi 的边界

“目录已登记”“工具能在 Worker 中执行”“工具完整定义已进入当前模型请求”是三件事。平台先把选定的源工具包装成可调用工具，并提供经过授权过滤的可用范围；Pi 负责工具循环和加载机制，调用时仍经过平台网关。

优先使用 Pi 的工具配置和 Tool Search／MCP 扩展做按需发现与加载；SDK 中显式配置对应扩展。自有 HTTP、RPC 或脚本工具可以直接包装，不要求原 DBA 小组先改成 MCP。平台目录的权限、语义匹配、质量排序和外部存储接入，需要通过适配与扩展连接，不能假定 Pi 内置搜索已经完成这些业务能力。

搜索候选卡片不能代替完整可调用定义。完整定义包含参数结构及含义、必填项、单位和限制，并绑定实际执行包装器；工具集合变化在后续模型请求中生效。调用记录保存工具与适配版本，防止同一名称在调查中悄悄改变含义。随着 Topic 结束收敛活跃工具集，不让按需加载最终变成全量常驻；具体收敛与压缩方式按采用的 Pi 版本验收。

Skill 使用范围限定的资源加载：首层仅展示本领域与任务相关简介；已知慢 SQL 场景主动装配核心方法，其他分支按需检索后读取正文。大量 Skill 也要先筛选，不能因为“只加载简介”就把上千条简介全写进系统提示。加载 Skill 是读取方法，不等于安装程序、执行脚本或获得其中列举的全部工具权限。[Pi SDK 配置边界](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)、[Pi Skill 加载方式](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md)

#### 13.7.4 结果二次处理与证据检索

处理链为：复用现有工具调用 → 在访问和保留策略允许范围内保存源结果／引用 → 检查大小、相关性与当前预算 → 选择直送、必要解析、筛选聚合或按引用读取 → 向 Pi 返回有界内容。模型解释仅在需要时增加，不强制将所有结果再次总结。敏感字段对模型提供脱敏视图，凭据不得混入普通证据。

通用处理器优先覆盖 JSON、表格／CSV、文本日志等常见格式，再用映射规则处理专有字段。程序负责确认过的单位转换、计数、聚合与时间比较；模型负责解释复杂片段和辅助定位，不让模型随意重算大批数字。解析失败时仍可提供有界原文和明确失败状态，不能生成“没有异常”的成功摘要。

每次结果分别保存请求的范围、源实际覆盖范围、源采样／截断情况、平台处理覆盖范围、来源与处理版本。引用可定位至原始记录、行号、时间点或统计查询条件。若源返回单位不明、仅当前值、只给前若干项或已删除历史记录，平台标为未知／不完整，不补造成完整现场。

例如慢 SQL 工具返回大量文本，平台可解析 SQL 指纹、执行时间、扫描行数，统计异常指纹并返回证据编号。主调查者再按“Q17、事发时段、代表性记录”过滤取片段，或查询事前事后统计；不必先读全量材料。检索无命中只证明当前材料和条件下未找到，需检查覆盖范围与解析状态。必要时继续取源端分页或更早数据；确无能力时记录缺口并转人工。

向源维护小组发起补充需求的条件应具体：必要数据原本未返回、无历史或分页、关键字段语义无法确认、源访问方式不能满足授权、无法区分失败与空结果等。说明影响哪个场景、已经做过哪些平台适配，以及最少需要补什么，不发起全面格式改造。

#### 13.7.5 找错或漏掉工具的纠正

| 失败点 | 识别办法 | 处理方向 |
|---|---|---|
| 能力尚未登记 | 目录中没有对应数据源或用途 | 补接入资产，不通过改提示词假装解决 |
| 筛选过严或元数据错误 | 应适用能力被错误版本／领域条件排除 | 修目录；只放宽非权限条件，不越过授权 |
| 搜索漏召回 | 所需能力在范围内但未进入候选 | 加别名、用途描述、分类浏览，按案例增强搜索 |
| 模型选错 | 已返回正确候选，却选了当前值工具调查历史现场等不适用能力 | 明确不适用条件及例子；执行前核对关键范围 |
| 参数或调用失败 | 时区、实例映射、必填参数、权限、超时不符合 | 平台校验与反馈，限制重试，不解释成无故障 |
| 数据或解析失败 | 返回为空、已截断、单位不明、结构变化 | 标记实际状态，查源结果，修处理规则或请求必要补充 |
| 漏查关键分支 | 未取得方法要求的必要证据却下结论 | 维护待查清单；补查或输出有缺口的候选判断，不能宣布根因确认 |

慢 SQL 方法中的检查项按适用性标记“已取得／不适用／不可取得／待检查”，覆盖主要查询变化、执行次数与扫描量、资源等待、锁和近期变更等方向，不要求所有工单机械调用所有工具。结束调查时对照这份清单，比单靠模型自称“已查完”更可靠。

评测分别统计能力候选覆盖、工具选择、有效调用、结果解析、证据覆盖和最终人工补做量。用“症状相似但正确工具不同”的案例检查搜索与选择：当前 CPU 高、历史 CPU 峰值、锁等待导致慢、某 SQL 扫描放大等。记录每次候选与过滤理由，避免失败后只能猜是模型、搜索还是源工具的问题。

### 13.8 工具结果与压缩保护的评审结论

**当前判断：用户关于大结果治理与 Topic 保留的方向成立，但“内容多就清理”和“Topic 不参与压缩”本身不能保证正确。** 架构需要分别解决结果进入上下文之前的控制、已积累会话的压缩，以及调查状态的持续维护。Topic 是业务调查状态的一种组织形式，不是模型天然不会遗忘的特殊区域。

#### 13.8.1 统一治理原则而非统一所有业务 Schema

不论结果是 JSON、表格或文本，都应用大小预算、来源记录、完整性标记和回查机制。可以给模型提供轻量结果说明：调用状态、当前可见内容、原结果引用、筛选／截断情况、下一步读取方式；内部业务字段保留差异。

通用大小控制不需要先理解每个业务字段；正确聚合、单位换算和异常解释则需要相应语义。不能声称一个通用清洗模型可无差别理解所有 Schema，也不应因为格式不同而要求所有源工具重做。

| 结果情况 | 当前建议 |
|---|---|
| 短且与当前问题相关 | 直接提供，不为处理而重复总结 |
| 体量小但细节暂时无用 | 保留简短观察或引用，按需读取 |
| 大量结构化记录 | 外部保存，按指纹／时段过滤和统计，读取代表性记录 |
| 大量非结构化材料 | 保存后检索与分块读取，需要时对有界片段做模型解释 |
| 格式未知或解析失败 | 返回状态、限制和有界片段／引用，避免回退到全量直送 |

筛选要尽量可逆：从当前模型输入中移走，不等于从证据中删除。保留必要时间范围、分布、异常样本和反对证据；只取头部记录可能丢掉短暂锁等待或低频关键事件。优先使用源工具已有的过滤、分页参数减少无关采集，不要求源工具为此重新设计。

#### 13.8.2 单次与累计上下文共同控制

一份结果不大，连续调用或并行调用仍可能累积超限。预算需考虑系统规则、工具定义、已加载 Skill、Topic 状态、近期对话、本批结果，以及模型后续输出与工具调用空间。阈值按模型和业务效果校准，不能只等服务端报超长再处理。

平台应在返回工具结果给 Pi 之前控制内容量，并在下一轮模型请求之前检查整体预算。复用 Pi 的会话压缩和扩展边界，但不把 Pi 默认摘要当成 DBA 关键状态的完整性保证。[Pi 压缩机制](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md)

#### 13.8.3 Topic 保存什么以及如何保护

Topic 应是可更新的调查记录，至少包含：当前问题与资源时段、有效的用户修正、已确认观测及证据引用、候选原因及支持／反对依据、数据限制、已经检查和执行的内容、未决问题、下一步。已执行生产动作以执行系统的真实记录为准，Topic 只引用，不另造一套执行事实。

例如某慢 SQL Topic：Q17 扫描量变化已取得证据，索引原因仍为候选；锁等待取证超时，尚未排除；目前仅诊断，未执行变更；下一步查计划与相关时段等待。压缩后不能变成“已确定缺少索引，建议执行”，也不能把“没查到锁数据”改成“没有锁”。

状态随关键发现、用户修正和动作变化及时更新，不等到窗口快满才临时总结。压缩前核对最新状态版本与引用；旧会话生成辅助摘要；压缩后从持久状态装配当前工单约束、活跃 Topic、必要新证据及近期消息。检查未决项、反对证据和动作状态是否仍可见，缺失时重新读取或暂停继续调查。

“不丢 Topic”指关键状态可恢复，不要求原文全部永远常驻。活跃 Topic 使用有界状态，已结束 Topic 保存简短结果和引用后归档，发现新证据可重开；防止 Topic 自身膨胀成第二份无限聊天记录。

#### 13.8.4 可靠性边界与验证

程序可检查范围、必需字段、证据引用、状态版本和动作记录，不能证明模型理解完全正确，也不能保证所有尚未被识别的重要信息已进入 Topic。保留原材料、反对证据、人工纠正及可重开的调查路径，用业务案例检验压缩后是否仍能做出合理下一步。

至少比较压缩前后的：工单范围、观测与假设区分、待查项目、失败检查、已执行动作、关键引用、后续工具选择；同时检查多次压缩后的错误累积。少占 token 但导致重复取证、错误排除原因或重复执行的方案，应判为失败。老师式评审应明确这些成立条件与局限，不将用户设想简单附和为最终设计。

### 13.9 主语言与技术栈取舍

**原推荐（以直接复用 Pi Coding Agent SDK 为前提）：TypeScript＋Node.js，已有 Go／Python 工具通过 MCP 或现有接口接入。** 该建议尚未得到用户最终确认；现在进入轻量循环／自主内核复审，不能继续仅因 Pi 使用 TypeScript 决定整个平台语言。新实施目录无应用源码，也不受旧目录模板限制。

平台主要负责工单状态、任务协调、能力发现、Tools／Skills 装配、证据组织、上下文控制、Topic 与人工工作台；数据库底层操作与已有专业能力主要由工具服务提供。主语言应围绕新增平台的职责、集成成本和持续维护选择，不必沿用所有上游工具的语言。

| 路线 | 主要收益 | 主要代价与适用条件 |
|---|---|---|
| TypeScript 平台＋Pi SDK | 直接使用运行接口、事件和扩展，减少跨语言映射；可与前端共享契约，适合小团队维护核心流程 | 仍要进行运行时输入校验；重计算和大结果处理不能阻塞主线程 |
| Go 平台＋Pi RPC／独立 Worker | 可复用成熟 Go 平台模板和维护团队，服务与运行层分开 | Pi 仍需自己的运行环境；增加跨语言协议、进程控制、取消和故障定位工作。已有 Go 工程体系构成硬约束时更值得采用 |
| Python 平台＋Pi RPC／独立 Worker | 便于复用以 Python 为核心的应用与数据处理体系 | 同样增加 Pi 运行边界；如果现有优势主要在上游工具，未必需要让整个新平台承担这一成本 |

Pi SDK 提供进程内 TypeScript 接口；RPC 模式用于跨语言或隔离子进程接入。因此采用 Go／Python 并非不可行，也不必然需要额外微服务，但需要维护运行环境和协议边界。[Pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)、[Pi RPC](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)

MCP 提供跨语言的工具连接方式，官方有 TypeScript、Go、Python SDK。它不要求服务重写成平台语言，也不替平台完成业务授权、预算、结果控量或任务恢复。已有 HTTP／RPC 能力可直接适配，不为统一名称强制改造全部上游服务。[MCP SDK](https://modelcontextprotocol.io/docs/sdk)

**推荐的技术基线与采用时机：**

| 部分 | 当前建议 | 采用范围 |
|---|---|---|
| 主平台与调查 Worker | TypeScript、与 Pi 兼容的 Node.js LTS、Pi SDK | 优先确定，固定经验证的依赖版本 |
| API | Fastify，按业务模块组织；JSON Schema 等运行时校验 | 增加接口时引入；TypeScript 类型不能验证外部真实数据 |
| 工作台 | React＋TypeScript，前端构建默认可用 Vite | CLI 调查样板后按阶段实现；不要求为了控制台引入服务端渲染 |
| 持久业务数据 | 默认 PostgreSQL；公司已有可靠托管数据库时再比较复用 | 工单、Topic、任务、证据索引与反馈；独立于 Pi 会话 |
| 原始证据 | 本地演示可用文件；正式环境使用公司对象存储或 S3 兼容存储 | 同一存储接口下区分实现，不能把本地文件演示当生产恢复已验收 |
| 后台任务 | 优先已有任务设施；采用 PostgreSQL 且无现成队列时评估 pg-boss | API 和 Worker 可同仓库、分进程；外部动作去重和状态核对独立处理 |
| 大结果计算 | 流式读取、过滤聚合；重计算按需要用线程池、子进程或已有 Go／Python 服务 | 按真实瓶颈引入，不把大文件整块读入主线程反复处理 |

Node.js 的 Worker Threads 适用于 CPU 密集计算；普通异步 I/O 不需要都转成线程任务。这里的“后台 Agent Worker 进程”和“计算用 Worker Thread”是不同概念。[Node.js Worker Threads](https://nodejs.org/api/worker_threads.html)

第一版保持模块化应用加后台 Worker，同仓库共享约定，明确模块边界后按容量或故障隔离需要拆部署。框架不能代替持久化、执行归属、取消与恢复设计。新增系统暂不为语言分工而先建 Go API、Python 调度、TypeScript Agent 三套核心服务；确有现成团队或能力收益时再引入。

若后续发现公司不能运行 Node.js、长期维护团队有明确语言限制，或现有平台复用价值远高于重建，应重新审视平台主语言；Pi Worker 仍可保持独立边界。AI 辅助编码减少部分实现劳动，但不能消除多语言调试、升级和运维成本。

#### 13.9.1 Pi 以 SDK 依赖集成

原完整 SDK 路线通过项目依赖安装官方 Pi Coding Agent SDK，核对实际发布包与版本后锁定版本和依赖锁文件，在自己的 AgentRunner 模块中调用公开接口。官方当前 SDK 文档使用 `@earendil-works/pi-coding-agent`；SDK 在我们自己的 Node.js 进程中运行，不需要先部署一套远程 Pi 服务。当前是否采用此包已进入复审。[官方 SDK 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)

| 方式 | 当前用途与取舍 |
|---|---|
| 安装官方发布包 | 默认集成方式；业务代码、Tools、Skills、结果控制和 Topic 放在自己的项目中，通过配置、公开接口与扩展接入 |
| 单独检出并留存同版本源码 | 纳入学习与可控性方案，用于机制导读、核对行为和必要调试；阅读与归档不等于立即维护修改版 |
| Fork 并维护修改版 | 已有可复现问题且公开扩展无法满足时再评估；需要记录补丁、固定版本和持续回归，尽量向上游反馈 |

不直接修改 `node_modules` 作为正式实现，避免安装后变更丢失。SDK 升级先跑工具调用、大结果控制、压缩恢复和取消等回归，再更新版本。默认使用发布包是集成建议，不构成已经安装或已经证明所有业务需求能通过扩展实现的声明。

#### 13.9.2 Pi 升级与兼容维护原则

用户关注 SDK 更新是否影响平台，以及采用源码是否也要持续合并。当前建议是固定已验收版本、按收益和风险主动升级，而非跟随每个版本。使用源码也可固定提交；只有采用上游新变更时才需要合并与验证，维护修改版不能消除升级成本。

发布采用精确依赖版本、依赖锁文件和受控运行环境，避免部署时自动切换至最新版。重要缺陷修复、必要模型／协议兼容和有价值的新能力是主要升级理由；旧版存在必须修复的问题或外部服务停止兼容时不能无限冻结。

| 方式 | 升级时主要承担什么 |
|---|---|
| 官方 SDK | 检查公开接口、扩展、配置和行为变化，调整自己的接入代码并回归 |
| 未修改的源码固定提交 | 更新到目标提交、重新构建并验证，不因使用源码自动获得额外兼容保证 |
| 维护 Fork | 在接口和行为验证之外，还要处理自己的补丁与上游代码冲突，以及能合并但语义已变化的问题 |

Pi 调用集中在 AgentRunner／运行适配模块，工单、Topic、证据与动作状态使用平台自有约定；不将内部未公开接口或存储结构作为业务唯一依赖。此边界降低代码改动范围，不保证运行行为不受影响。编译通过仍可能存在压缩、工具调用、取消、重试或事件时序变化，不能只测试类型兼容。

升级流程为：查看目标版本说明与接口 → 在独立变更中升级 → 回归固定业务案例 → 小范围试用 → 扩大使用。回归覆盖工具发现与调用、大结果控量、Topic 压缩恢复、人工补充、取消、超时重试和会话读取；真实模型比较判断依据与业务结果，不要求逐字相同。尽量不要在同一次评估中同时修改 SDK、模型、Skill 和工具规则，避免效果变化无法归因。

进行中的调查原则上继续使用开始时绑定的运行版本，新任务再使用灰度版本；必须迁移时单独验证恢复。升级前保留旧构建与数据兼容说明，会话或业务数据结构有迁移时，评估旧版能否读取，不能承诺只改回依赖版本就能回滚。SDK、远程模型和工具服务版本分别记录；锁定 SDK 不能冻结外部服务变化。

#### 13.9.3 源码理解与上游不可用时的保障

原 SDK 路线的保障建议为“SDK 运行集成＋同版本源码留存和导读＋平台业务自建”。当前新增独立内核候选，此处保留复用路线的控制方法。使用 SDK 是复用形式，不代表代码不可读；掌握系统需要知道调用链、扩展边界、状态归属和失败行为。采用复用路线时应准确表述为“基于 Pi 构建，业务控制与 DBA 能力由平台自建”，不将 Pi 内核声明为本项目全自研。

Pi 仓库当前采用 MIT 许可，允许在遵守条件、保留相关声明的前提下使用、修改和分发代码。实际接入时留存所选提交及其许可证，依赖包和远程服务分别核对，不能将根目录许可推定为所有组成部分和模型服务的许可。[Pi 当前许可证](https://github.com/earendil-works/pi/blob/main/LICENSE)

| 上游变化 | 实际影响与应对 |
|---|---|
| 项目停止维护 | 已留存、已部署版本不会仅因停止维护自动消失；后续修复和兼容需由平台承担或选择替代 |
| npm 撤包、仓库不可访问 | 可能影响重新安装与构建；锁文件不包含全部依赖实体，需要源代码、依赖制品和构建产物留存 |
| 新版本许可或发布方式改变 | 保留当前取得版本的许可记录，按其条件使用；新版本另行判断，不强制跟随 |
| 外部模型、工具或其他在线服务停用 | 属于运行时依赖中断，SDK 本地留存不能解决；按各自的替代与恢复方式处理 |

撤包或删库本身不会删除本地已安装代码，但不能据此保证任意 Pi 版本及其依赖都没有运行时外部要求。选定版本后核对运行时网络、授权、动态下载和自动更新路径，明确构建阶段与运行阶段分别依赖什么。

**机制学习应对应实际调用路径：**

| 机制 | 要能解释与观察什么 |
|---|---|
| 模型调用与 Agent 循环 | 请求如何组装、工具调用如何解析执行、何时继续或结束 |
| 工具与 Skill 装配 | 哪些定义和正文进入上下文，搜索、加载与真实执行在哪里发生 |
| 会话与压缩 | 保存什么、压缩后如何重建、扩展能在哪些位置介入 |
| 事件、取消和错误 | 事件顺序、取消范围、重试行为及对外部工具的影响 |
| 平台扩展 | 结果控量、Topic、证据和业务状态如何接入，以及哪些内容由平台独立保存 |

为每项整理“公开入口 → 核心模块 → 扩展点 → 可运行实验”，引用实际采用提交的源文件与函数，避免只看最新版文档或背 API 名称。架构与实现文档配套说明能力来源和已验证范围，源码导读作为实现过程的一部分逐步补齐。

供应保障需覆盖选定源码与许可、依赖包及必要构建工具、锁文件、构建脚本、可部署产物和关键回归案例。目标是在不可访问公共 GitHub／npm 时仍能使用内部留存制品构建和部署；这不代表模型和远程工具也已能离线运行。该能力需实际演练，不能只凭缓存目录存在宣布通过。

平台保留自有的工单、Topic、证据、动作记录和导出约定，Pi 调用集中于运行适配模块。保留未来修补或替换运行层的路径，但替换仍需要会话、工具、事件和恢复行为适配及业务回归，不能承诺换一个实现即可无缝切换；首版不因此同时建设两套生产内核。

### 13.10 轻量循环与自主 Harness 的路线复审

用户最新补充使需求重点从“复用完整编程助手”转为“平台自主控制上下文、压缩和各节点埋点，可能仅需循环”。应先确定责任边界，再决定循环是否复用和主语言。因上游存在可管理风险而重写全部功能，不代表风险总量更低；自研会承担原本由依赖维护者负责的正确性、适配和缺陷修复工作。

#### 13.10.1 三层能力与两条候选

| 层次 | 实际需要 | 当前倾向 |
|---|---|---|
| 编程助手产品层 | 终端界面、代码编辑体验、完整插件分发等 | 不作为首版目标，不为这些能力集成完整 SDK |
| 平台 Harness | 上下文组装、结果准入、Topic、压缩、工具与 Skill 装配、观测、预算和业务恢复 | 核心策略由本平台定义、维护和独立验证 |
| Agent Loop | 发起模型请求、接收工具调用、执行并回传、继续或停止 | 比较复用 Pi 底层循环与自研小型循环 |

Pi 不只有 Coding Agent SDK。其底层 `pi-agent-core` 提供上下文变换、请求准备、工具调用前后处理与运行事件，能够作为轻量复用候选；自定义压缩与埋点本身不能证明需要重写。事件观察与能否同步改变执行是不同能力，必须按采用版本验证。[Pi 底层 Agent 文档](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)

| 候选 | 适合的要求 | 代价 |
|---|---|---|
| 自建 Harness＋Pi 底层循环 | 可接受少量 Pi 运行依赖，主要追求自己的策略与观测 | 仍需维护版本、消息类型及控制点适配，关键逻辑不能藏在不可验证的回调里 |
| 自建 Harness＋自研小型循环 | 明确要求生产运行不依赖 Pi 包，愿意维护核心循环 | 承担工具结果关联、流式中断、取消、并发、重试和状态一致性的验证责任 |

独立循环不要求更换语言，TypeScript 同样可以实现。若选择与 Pi 无运行依赖的小型内核、且无组织语言硬约束，当前可优先评估 Python＋FastAPI，方便集中实现调查逻辑和上下文实验；Go、Java、TypeScript 均为可行路线，长期维护团队与现成工程体系会影响选择。[FastAPI 文档](https://fastapi.tiangolo.com/)

#### 13.10.2 有限自研的范围与验收

自主实现的目标是业务控制权，首版不复制全部 Pi 功能。模型通信、MCP、存储和观测可复用成熟且可替换的基础库，不将所有网络协议、驱动都重写；这些依赖仍需固定、留存和验证。

核心循环至少需要正确关联模型工具调用与结果，校验参数、区分失败与空结果，在多轮中处理终止、轮次与费用预算、取消、超时和恢复。压缩及 Topic 由独立策略模块负责，循环通过明确接口调用，避免写成无法局部修改的大循环。

使用相同的模拟证据与判断规则验收，至少覆盖：正常多轮取证、工具失败、大结果、多个工具结果顺序、模型流式输出中断、用户中途修正、压缩前后状态、取消和 Worker 重启。工具请求在外部已执行但平台未记录时，必须核对实际状态，不能因自研循环就默认可重试；首版保持只读边界。

#### 13.10.3 节点埋点与同步控制

| 节点 | 需要观察什么 | 是否还需要控制能力 |
|---|---|---|
| 工单与任务启动 | 目标、资源时段、领域、版本、预算 | 授权与任务归属检查 |
| Tools／Skills 发现 | 查询、过滤原因、候选、选择与装配结果 | 决定允许加载哪些能力 |
| 上下文组装 | 内容来源、材料引用、估算 token、Topic 版本、丢弃与保留理由 | 在发给模型前调整内容并检查总预算 |
| 模型调用 | 逻辑调用与实际重试、首响应及总耗时、用量、结束原因、错误 | 超时、取消、重试及预算约束 |
| 工具执行 | 校验、授权、实际请求发送、完成、失败和取消状态 | 调用前可阻止，不能把事件开始等同于源工具已执行 |
| 结果处理与保存 | 原始大小、可见大小、处理方式、限制和证据引用 | 返回给模型前必须完成结果准入 |
| Topic 更新 | 状态版本、修改依据、未决事项变化 | 必须记录的业务状态按要求提交 |
| 压缩与恢复 | 触发理由、前后体量、引用与状态检查、恢复缺口 | 可修正、重新读取或暂停 |
| 任务结束与接管 | 实际完成阶段、停止理由、后续事项 | 循环结束不能直接等于业务解决 |

每条观测按工单、运行、轮次、子任务、Topic、工具调用和重试关联；使用 OpenTelemetry 等标准观测接口的具体方案后续确认。区分 Trace、事件日志与统计指标，不将全部工单标识直接变成高基数指标标签。记录可观察的依据和决策结果，不声称能够观测模型内部真实推理。

观察回调不能代替同步控制点。例如“结果处理完成并保存后才进入下一轮”需要可等待的提交边界，不能只在异步日志订阅者里写文件。Pi 原始循环事件流与 Agent 类的等待行为有区别，复用时必须核对；自研时则需明确事件发生在实际动作前还是后。

调试观测可按容量异步、采样或降级，关键审计与业务状态不能因此默默丢失。默认记录元数据和证据引用，不把所有日志、模型输入输出和逐 token 内容复制进每条埋点，避免观测系统自身膨胀并混入凭据或不必要的客户数据。

#### 13.10.4 AI 辅助吸收上游改进

#### 13.12.1 实际接入方式

该项目使用 Python 后端和任务 Worker，在外层管理任务、会话、执行状态、事件与产物；`OpenCodeRuntimeAdapter` 使用项目自己的 `httpx` 客户端调用独立 OpenCode Server，没有将 OpenCode 源码翻译成 Python。内部的模型调用和工具循环仍由 OpenCode 执行。

存在三种运行情况：

- 未启用沙箱：连接配置中的固定 OpenCode 服务。配置类默认 `sandbox_enabled=False`。
- 启用本地沙箱：每个所属会话启动独立 `opencode serve` 子进程，分配独立端口、工作目录与 XDG 状态目录；这是进程和目录分开，不是容器或完整安全隔离。
- 启用腾讯云沙箱：通过 AGS 控制接口创建或连接实例，使用兼容 E2B 的文件／命令通道启动 OpenCode，再通过实例的 HTTP 地址调用。仓库生产配置启用了该分支；线上配置未经此次核实。

普通执行链路是：Worker 领取任务 → Adapter 获取会话所属沙箱／固定客户端 → 按需要挂载 MCP → 创建或复用 OpenCode 会话 → 先订阅事件，再异步提交提示词 → 转换事件并持久化、展示 → 收取最终消息与输出产物。沙箱模式按平台会话复用环境，不是每个工具调用都重建一个环境。

#### 13.12.2 可以借鉴的边界与限制

1. **平台语言与引擎语言可以不同。** Python 可以通过协议使用完整外部引擎；选择自有循环，应基于控制需求和维护成本，而非误认为 Python 无法接入现成引擎。
2. **平台会话、沙箱、引擎会话应分别管理。** 该项目允许不同阶段共享沙箱和文件，同时使用不同 OpenCode 会话；文件共享不要求把全部聊天历史放在一起。具体到 DBA 工单，任务、调查分支和 Topic 的关系仍需单独设计。
3. **事件观测不等于内部控制。** 项目能收取工具开始、完成、失败等事件，但不能仅凭外层收到了结果，就断定它能在每次模型请求前替换上下文，或在工具结果进入引擎历史前拦截筛选。这些必须验证具体引擎接口，必要时修改引擎或自建循环。
4. **沙箱解决执行环境问题，不能代替上下文治理。** 提供文件、脚本与依赖环境，不会自动实现工具搜索、结果控量、Topic 维护和压缩保护。DBA 平台可以保留自有循环，把沙箱作为按需使用的分析工具；调用现有只读 MCP 并不天然要求独占沙箱。
5. **环境恢复与调查恢复是两件事。** 该项目实现了运行中保活、可选工作区快照、替换实例前恢复，以及引擎会话不存在时的一次重建重试。文件／引擎存储恢复不能替代业务证据与调查状态恢复，也不能保证故障前最后一步一定已持久化。
6. **抽象接口仍需检查实际耦合。** 项目有 RuntimeAdapter，但云驱动仍写死 OpenCode 启动命令和部分运行约定。接口存在不代表替换引擎零成本；版本、配置、事件协议与会话存储都属于需维护的运行依赖。

当前保持已确认的 Python 主语言；自有小型 Loop／Harness 仍为优先评审建议。该项目作为“Python 业务层＋外部引擎＋可选沙箱”的实证对照，不据此自动修改技术路线。

### 13.13 现有 Python 服务背景与推进原则

用户澄清 agent-platform 仅供参考；同事口头反馈已实现一版 Python DBA 服务，但效果不好，等待用户去优化或重构。目前用户没有代码，只是听说。不能据此认定现有服务使用什么框架、存在什么具体缺陷、已上线或必须重写；也不能将先前查看的空仓库或 agent-platform 当成该服务。

当前建议采用“Python 主语言保持、目标能力先定、取得现状后决定改造范围”的路线：

1. **取得可比较的基线。** 收集一批脱敏真实工单、对应诊断时段的工具数据或记录、DBA 认可的判断依据、现系统执行轨迹。优先选慢 SQL 等一个可界定场景，覆盖成功与失败，不只看最终回答是否像样。历史动态数据不可重现时，明确回放与当前查询的区别。
2. **先定位失败发生在哪一环。** 分别检查问题理解、工具发现、调用参数与授权、证据完整性、结果筛选、上下文／压缩、推理、方案可执行性和验证。模型能力也是待验证因素；不预设效果差一定来自模型、提示词或 Loop。
3. **补齐最小业务闭环。** 优先对真实失败有解释力的模块：执行轨迹、工具目录与调用治理、大结果留存和检索、调查状态、结论证据与验证。已有模块达到要求则复用，缺失部分再建设，不强制引入所有候选组件或多 Agent。
4. **用相同案例决定局部改造。** 先保持案例、证据和模型配置可比较，逐项验证变化；确认关键控制点无法实现、故障恢复或维护成本不可接受等实质障碍后，才考虑替换内核或较大重构。后续更换模型时单独比较，也记录模型运行的不确定性。
5. **生产改造先交付评估结论，再实施。** 明确保留什么、补什么、替换什么及原因，配套目标架构和实施文档。用户随后明确希望独立搭建学习原型，可以先行推进，见第 13.14 节；该原型不被自动认定为生产替代版本。

本节约束生产改造取舍，不阻止用户已明确要求的独立原型建设。Python、业务策略和证据／调查状态由平台掌握、分阶段用案例验证的方向保持；生产框架、循环来源、沙箱和多 Agent 数量仍待评估。

#### 13.14.1 原型路线建议

延续 Python：自有小型 Agent Loop＋业务 Harness，外层按需要使用 FastAPI，基础模型客户端、类型校验、MCP 和存储复用成熟库。先用命令行跑通核心，HTTP 接口和工作台随后接入；一个仓库按模块组织，不先拆多套微服务。原型从本地文件与轻量状态存储起步，持久化接口保持清楚，生产存储按现状另定。模型尚未提供时，可用脚本化模拟响应验证流程，但不能把此结果称为模型诊断效果已验证。

Pi 用作逐模块学习和行为对照，不整仓翻译。实施时固定所参考版本／提交，分别说明循环、上下文转换、工具调用前后处理、事件与取消在 Pi 中的位置，再对应自己的实现和用例。[Pi Agent 官方说明](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md) 中的上下文转换、工具前后钩子和运行事件可作为学习入口；这些机制与 DBA 业务策略分开看。[FastAPI](https://fastapi.tiangolo.com/) 仅作为接口层候选，不负责 Agent 调查逻辑。

#### 13.14.2 模块与调用关系

| 模块 | 主要职责 | 原型处理方式 |
|---|---|---|
| 任务入口与执行管理 | 接收工单、维护状态、启动／取消执行 | 自己实现业务层，CLI 先行，HTTP 后接 |
| Agent Runner／Loop | 每轮组装请求、调用模型、分派工具、继续或停止，传递取消与预算 | 参考 Pi，实现有限能力并验证 |
| 上下文管理 | 根据当前目标、Topic、近期交互与证据选择本轮材料，必要时压缩 | 自己实现策略，明确模型输入与完整历史不同 |
| Tools／Skills 目录与装配 | 维护描述、适用范围、搜索、依赖及按需暴露；Skill 提供调查方法 | 自己实现业务目录，先用少量模拟能力 |
| 工具执行网关 | 校验参数、权限和预算，适配本地模拟工具／MCP／HTTP，记录结果 | 自己实现治理，复用基础连接库 |
| 证据保存与检索 | 原始结果先留存，返回有界视图与引用，按需筛选和读取 | 自己实现策略，避免把全部原始结果直接传回上下文 |
| Topic／调查状态 | 保存已知事实、假设、排除项、缺口、下一步和证据引用 | 独立于消息压缩持久化；自动更新需校验，不保证语义无损 |
| 运行事件与回放评估 | 关联任务、轮次、模型调用、工具调用、证据及版本，观察失败原因 | 从第一轮纳入；保存必要、受控的请求视图，不要求记录隐藏思维过程 |
| 模型适配器 | 转换供应商协议，提供统一请求与响应边界 | 复用基础客户端，保留协议差异处理与可替换接口 |

基本流程：任务建立 → 装配适用 Skill／初始能力 → Loop 请求上下文 → 模型提出工具调用 → 网关执行 → 原始结果进入证据存储 → 有界结果关联原工具调用返回 → 更新／校验 Topic → 下一轮组装 → 检查结论证据与停止条件 → 保存报告和运行事件。模型主动搜索工具时也经过同一网关，搜索不绕过授权；工具定义的动态变化在后续请求中生效。

#### 13.14.3 学习顺序与验证边界

先做单 Agent、一个慢 SQL 样例和少量模拟 Tools／一个 Skill；跑通多轮工具调用、停止与事件。再加入大结果、证据检索、Topic、上下文预算及压缩前后对照；然后引入失败、超时、取消和状态恢复；有模型后验证实际工具选择与诊断。最后用同一任务比较单 Agent 与有明确分工的两个 Agent，观察证据交接、重复调查、耗时和调用成本，不将 Agent 数量增加视为自然升级。

每一步应能展示输入、输出、关键状态变化和可复现用例，并说明 Pi 参考点与自建边界。当前原型用于形成理解和验证能力；生产采用哪部分，待取得真实服务和工单后另行决定。

#### 13.14.4 Pi 对照内核的目录与可替换边界

用户提出将 Python 移植的 Pi 内容集中在独立目录，清楚识别来源，方便后续插拔改造，同时询问 Demo 是否直接使用 TypeScript 更合适。当前建议继续 Python 原型；如果目标改为直接运行官方 Pi SDK、逐行调试原版实现，则 TypeScript 更直接。此为取舍说明，不登记为用户已最终批准实现范围。

需严格区分三种来源：运行官方 Pi 代码才称 Pi 原生；从指定源码移植到 Python 的部分标注 Pi 移植及改动；仅参考机制、自行设计的部分标注设计借鉴。不能把全部 Python 内核统称 Pi 原生，也不承诺有限实现与官方行为完全等价。

建议把内核集中在 `app/runtime/pi_reference/`，由 `app/runtime/contracts.py` 定义平台自己的运行输入、事件、取消及依赖边界；DBA 上下文、Topic、证据、工具搜索、Skill 和权限策略放在 `app/harness/` 与业务模块，模型及 MCP／HTTP 连接放在 `app/adapters/`。这是规划目录，尚未创建。内核调用注入的上下文组装与工具执行接口，不直接依赖 DBA 数据库表、慢 SQL 规则或供应商私有消息类型。

目录隔离只是便于阅读；真正可替换依靠接口、依赖方向和可验证的行为约定。上下文策略和工具结果筛选应能独立替换，业务层不导入 `pi_reference` 内部类。只为已知替换点设置简单接口，不先建设通用插件市场。替换内核后仍要验证工具调用关联、错误、取消、事件及状态兼容；进行中任务不默认无缝切换运行版本。

配套 `docs/pi-mapping.md` 记录参考提交、源码路径／函数、对应 Python 模块、来源类别、保留与改变的行为、尚未实现项和验证用例。先实现消息与工具调用关联、有限循环、事件及取消等必要子集，不整仓翻译 Pi，也不把其模型协议层和完整 Coding Agent 产品功能全部搬过来。

#### 13.14.5 独立 TypeScript 前端与调查工作台

用户认可上一轮方案，并询问是否需要前端，建议采用独立 TypeScript 项目。当前推荐建设轻量工作台，便于观察完整调用链、比较实验和讲解架构；不只展示最终聊天回答。建议 TypeScript＋React＋Vite，组件方案尚未作为用户已批准事项。[React 官方文档](https://react.dev/learn/build-a-react-app-from-scratch) 给出了 Vite 的 React TypeScript 工程入口。

此前建议同仓库双工程，已由用户最新指定的两个独立仓库替代：后端 `/Users/baiml/PycharmProjects/support-platform`，前端 `/Users/baiml/PycharmProjects/support-platform-fe`。前端维护自己的依赖和构建，后端维护 Python 工程配置。第 13.14.4 节的 `app/runtime/`、`app/harness/` 等目录直接归于后端仓库，不再套额外 `backend/` 目录。

第一版以一个工单调查工作台为主：输入工单／选择样例；查看执行时间线和工具状态；按轮查看模型输入材料与实际输出、已装配 Tools／Skills；检查原始证据的有界预览、筛选结果和 Topic；展示最终结论、证据与验证方法。上下文内容和证据按需分页／检索加载，不把后端保存的全部大结果一次传入浏览器。

通过 HTTP 创建任务、查询状态、读取材料及提交取消／补充信息，通过 SSE 接收执行事件为当前通信建议。后端是任务状态与权限的权威来源，独立执行 Agent；前端负责交互和展示，模型凭据与真实工具执行留在后端。刷新或关闭页面不等于取消任务；初期可先刷新后查询任务记录，断线恢复时再基于持久化事件序号补取，不能仅有实时页面内存。

实施顺序仍是核心循环先可运行，然后接薄接口与页面，逐模块扩展观测能力；前端不承担另一个 Agent 内核，也不据此重新将后端改成 TypeScript。
